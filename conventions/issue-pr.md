# 이슈·PR 공통 규칙

이슈와 PR을 만들고, 머지하고, 닫을 때 모든 저장소에 같이 적용하는 규칙. 제목·커밋·브랜치·이슈 연결 키워드는 `conventions/git.md`, 리뷰 승인 조건은 `conventions/code-review.md`

## 분류 방식

| 무엇을 나누나 | 어디에 기록 | 값 | 필수 |
|---|---|---|---|
| 작업 유형 | 이슈 Type(조직 이슈 유형) | `Feature`(기능 추가), `Bug`(오류 수정), `Task`(문서·설정·운영 작업) | 이슈 필수 |
| 프로젝트 | 조직 Project "BOAZ-website project"의 Project 필드 | 홈페이지 운영 & 유지보수, 관리자 페이지 개발, Product Management, 온보딩, Terraform Migration, SRE & 장애 대응, Design System 구축, 서비스운영팀 업무 | 이슈 필수 |
| 우선순위 | 같은 Project의 Priority 필드 | 긴급(분홍), 높음(빨강), 중간(노랑), 낮음(파랑) | 이슈 필수 |
| 작업 종류 | 작업 종류 라벨 9종 | 아래 "라벨" | PR 필수(제목에서 자동) |
| 기능 영역 | 저장소 기능 라벨 | 저장소가 정함(예: backend의 `auth`, `recruitment`) | 선택 |

- 이유: 한 프로젝트가 여러 저장소에 걸침(예: 관리자 페이지 개발 = frontend_admin, backend, backend-docs). 저장소별 라벨로는 저장소마다 같은 라벨을 맞춰야 하고 한 곳에서 빠뜨리면 필터에서 빠지므로, 프로젝트는 조직 Project 필드 한 곳에서 정의함
- Project 필드 값은 Notion 티켓의 Project 속성과 같은 이름을 씀. 값을 추가·변경할 때 Notion과 함께 바꿈
- Project 값 판정 기준(위에서부터 먼저 맞는 것)

| 순서 | 조건 | 값 |
|---|---|---|
| 1 | product-infra WBS 티켓 ID(STA, NET, IAM, STO, OBS, CMP, RDB, CDN, DEP, SEA)가 붙은 이전 작업과 이전 계획 에픽([테라폼] Migration Planning) 작업 | Terraform Migration |
| 2 | WBS 밖의 인프라 운영: 운영 서비스의 배포·CI/CD와 릴리스(라이브러리 패키지 릴리스는 규칙 3), DB 운영·업그레이드, 경보·모니터링 운영, 시즌 전환 실행, 권한 정리, 장애 기준과 절차(원복, 마감 연장, 운영 시험) | SRE & 장애 대응 |
| 3 | 제품 코드나 설정을 바꾸는 개발 작업(기능, 버그 원인 수정, 테스트, API 문서)과 그 제품의 기획(기능 명세서, WBS, IA). 운영 DB에 공고·문항을 넣는 등 개발 담당이 하는 데이터 작업 포함 | 그 제품의 값(홈페이지 운영 & 유지보수, 관리자 페이지 개발, Design System 구축) |
| 4 | 코드 변경 없이 운영진이 하는 일: 콘텐츠 정리·업로드(활동사진, 기술블로그, 수료후기, 프로젝트), 업로드 가이드 | 서비스운영팀 업무 |
| 5 | 신규 팀원 합류와 인계 자료(README, 명세 정비 등 온보딩 에픽 작업) | 온보딩 |
| 6 | 어느 프로젝트에도 속하지 않는 PM 일반 업무: 전체 일정, 프로젝트 간 우선순위 조정, 보고, 팀 전체에 적용하는 운영 규칙(R&R, 스프린트, 협업 절차·템플릿, 플레이북). 한 저장소 안의 협업 규칙·CI·템플릿 설정은 규칙 3(그 저장소 제품의 값) | Product Management |

- SRE & 장애 대응의 정의: 운영 중인 서비스를 안전하게 배포하고, 관측하고, 장애에서 복구하고, 인프라를 유지하는 일
- Product Management의 정의: 여러 프로젝트에 걸친 운영팀 전체의 계획과 관리. 분기·시즌 로드맵, 프로젝트 간 우선순위와 인력 배분, 진행 보고, 회고, 팀 운영 규칙(R&R, 스프린트, 협업 절차). 특정 제품의 기획(명세서, WBS, IA)은 그 제품 값으로 분류함
- Terraform Migration은 끝이 있는 프로젝트. product-infra Phase 5 인수 판정(OPS-07)이 끝나면 값을 보관하고 이후 인프라 작업은 SRE & 장애 대응으로 분류함. 두 값을 합치지 않음(이전 이력 보존)
- 한 이슈에 두 성격이 섞이면 이슈를 나누고 상위 이슈로 묶음. 장애는 원인 수정(앱 코드)은 제품 값, 탐지·복구·재발 방지 체계는 SRE & 장애 대응
- 옵션을 고칠 때는 Project 웹 화면에서 함. API로 옵션 목록을 바꾸면 이미 지정한 값이 모두 지워짐
- 프로젝트 값에는 기수를 넣지 않음. 기수별 작업 묶음(예: "28기 리크루팅")은 상위 이슈(Parent issue)로 만들고 하위 이슈를 연결함. Notion Epic 링크는 상위 이슈 본문에 둠
- 여러 프로젝트에 걸치는 이슈는 주된 목적의 프로젝트 하나를 고름
- 우선순위 기준은 `org/pm-guide.md` "4. 티켓 우선순위"(Notion 티켓과 같음)
- 이슈에는 작업 종류 라벨을 붙이지 않아도 됨(Type과 같은 정보). PR의 작업 종류 라벨은 제목의 `[Type]`을 보고 자동으로 붙임

## 이슈

| 항목 | 규칙 |
|---|---|
| 담당자(Assignee) | 반드시 지정. 이슈를 만든 사람. 다른 사람이 작업을 맡으면 그 사람을 추가하거나 바꿈 |
| Type, 프로젝트, 우선순위 | 반드시 지정("분류 방식") |
| Project 편입 | 이슈를 조직 Project "BOAZ-website project"에 넣음. 자동 편입이 없는 저장소는 작성자가 넣고, 권한이 없으면 PM이 분류할 때 넣음 |
| 본문 | 일반 업무 이슈 템플릿 사용. 체크리스트(`- [ ]`)로 완료 조건을 적음 |

- 이유: 담당자가 없는 이슈는 진행하는 사람 없이 남고, 유형·프로젝트·우선순위가 없으면 보드에서 급한 일을 고를 수 없음. Project 밖의 이슈는 우선순위 목록에서 보이지 않음
- 이슈를 대신 만들어 준 경우(예: 회의 결정을 PM이 이슈로 옮김)에도 만든 사람을 먼저 지정하고, 작업자가 정해지면 작업자를 추가함

## PR

| 항목 | 규칙 |
|---|---|
| 담당자(Assignee) | 반드시 지정. PR 작성자(작업한 사람) |
| 리뷰어(Reviewer) | 반드시 지정. 작성자가 아닌 사람 1명 이상(PM 또는 해당 Product의 다른 팀원). 리뷰어가 없는 PR은 리뷰를 시작하지 않음 |
| 이슈 연결 | 이슈 전체를 처리하면 `Closes #번호`, 일부만 처리하면 `Refs #번호`(`conventions/git.md` "PR 제목") |
| 작업 종류 라벨 | 제목의 `[Type]`에 맞는 라벨 1개. 자동으로 붙고, 제목을 고치면 라벨도 바뀜 |
| 본문 | PR 템플릿 사용 |

## 체크리스트 완료와 머지·종료

| 대상 | 규칙 |
|---|---|
| PR 머지 | PR 본문의 체크리스트가 모두 체크되어 있어야 머지함 |
| 이슈 종료 | 이슈 본문의 체크리스트가 모두 체크되어 있어야 닫음 |
| 체크하지 못한 항목 | 머지·종료 전에 항목마다 사유를 댓글로 남김. 예: "해당 없음: 엔티티 변경 없음", "후속 이슈 #123으로 옮김". 사유 댓글이 있으면 머지·종료할 수 있음 |
| `Closes`로 자동 종료되는 이슈 | 리뷰어가 승인 전에 연결된 이슈를 열어 모든 항목이 체크됐거나 항목별 사유 댓글이 있는지 확인함. 이슈 일부만 처리한 PR은 `Refs`를 씀 |
| 직접 닫는 이슈 | 닫는 사람이 같은 내용을 확인함 |

- 이유: 체크리스트는 완료 조건이므로, 체크하지 않은 채 머지·종료하면 무엇이 빠졌는지 나중에 알 수 없음
- 후속으로 미루는 항목은 후속 이슈 번호를 사유 댓글에 적음

## 프로젝트 값과 저장소 추가

### 새 Project 값 추가

- 기준: "분류 방식"의 판정 표 1~6에 맞는 행이 있으면 기존 값을 씀. 새 값은 아래 셋을 모두 만족할 때만 만듦
  - 기존 정의로 판정할 수 없음
  - 이슈가 5개 이상 생길 예정
  - 기수 묶음이 아님(기수 묶음은 상위 이슈나 Notion Epic으로 만듦)
- 순서
  1. 제안 이슈(Type `Task`, Project 값 Product Management)에 값의 정의 한 줄과 판정 표에 넣을 행을 적음
  2. PM이 승인함
  3. 이 문서의 판정 표와 정의를 고치는 PR을 머지함
  4. Notion 두 DB(Engineering Ticket, 디자인 & FE Ticket)와 GitHub 조직 Project에 같은 이름으로 옵션을 추가함. GitHub 옵션은 웹 화면에서만 추가함(API로 옵션 목록을 바꾸면 기존 값이 모두 지워짐)
  5. 기존 티켓을 판정 표로 다시 분류함
- 종료: 정의에 끝 조건을 적음. 끝나면 값을 보관하고 다른 값과 합치지 않음(Terraform Migration 선례). 이후 작업을 넘길 값을 판정 표에 적음

### 새 저장소 추가

- [ ] 기존 이슈를 조직 Project에 넣고 Project 값을 지정함. 자동 추가 규칙은 무료 플랜이라 1개뿐이므로 PM이 일괄로 넣음
- [ ] 공통 이슈·PR 템플릿과 작업 종류 라벨을 backend와 같게 복사함
- [ ] 커밋 훅과 PR 제목 검사를 설정함
- [ ] AWS 배포가 필요하면 배포 롤 신뢰 조건을 `org/aws-access.md` 절차대로 설정함([org/aws-access.md](../org/aws-access.md))
- [ ] 워크스페이스 루트 `CLAUDE.md`의 저장소 표에 추가함

### 필수 값과 누락 점검

- 이슈 필수 값(Project, Priority, Assignee, Type)은 위 "이슈" 절 규칙을 따름
- Notion 티켓 필수 값: Project, 우선순위, GitHub Issue 링크
- 누락 점검: 스프린트 시작 때 PM이 확인함
  - GitHub Project에서 Project나 Priority가 빈 항목
  - 저장소별 `is:issue is:open no:project` 검색(저장소별 자동 편입 여부는 아래 "미결" 표)
  - Notion 두 DB에서 Project가 비었거나 GitHub 링크가 없는 티켓
- 빈 값 필터는 저장 뷰로 만들어 둠
- 이유: Project 값이 비면 프로젝트 필터 화면에서 빠져 누락을 알아채기 어려움

## 라벨

| 작업 종류 라벨 | PR 제목 | 색 |
|---|---|---|
| `⭐️ FEAT` | `[Feat]` 새로운 기능 | `#A2EEEF` |
| `🐛 FIX` | `[Fix]` 버그 수정 | `#D73A4A` |
| `🚑 HOTFIX` | `[Hotfix]` 운영 긴급 수정 | `#B60205` |
| `✏️ DOCS` | `[Docs]` 문서 | `#0075CA` |
| `🛠️ REFACTOR` | `[Refactor]` 동작 변경 없는 구조 개선 | `#FBCA04` |
| `🧁 STYLE` | `[Style]` 포맷팅 등 동작 변경 없음 | `#F9D0C4` |
| `🔎 TEST` | `[Test]` 테스트 코드 | `#C5DEF5` |
| `🚀 RELEASE` | `[Release]` `dev` → `main` 릴리스 | `#0E8A16` |
| `🧹 CHORE` | `[Chore]` 빌드·설정 등 부수 작업 | `#BFD4F2` |

- 이름·색·설명은 모든 저장소에서 같게 둠(backend 기준)
- PR 제목 검사와 자동 라벨 워크플로는 이 표를 대응표로 씀. 제목 검사가 허용하는 접두어는 모두 이 표에 있어야 함
- 기능 라벨(예: backend의 `auth`, `recruitment`, `monitoring`)은 저장소가 쓰고 싶을 때만 만들고 붙임. 조직 공통 규칙이 아니며, 프로젝트 구분에 쓰지 않음(프로젝트는 Project 필드)
- 사람 이름 라벨은 쓰지 않음(담당자는 Assignee)

## 템플릿

일반 업무용 이슈 템플릿 1종과 PR 템플릿 1종을 모든 저장소에서 같은 모양으로 씀. 섹션 이름과 순서가 같고, 저장소에만 필요한 확인 항목은 정해진 칸("저장소별 확인")에만 넣음

| 템플릿 | 섹션(순서 고정) |
|---|---|
| 이슈 | 작업 내용(무엇을 왜) / 작업 상세 내용(체크리스트, 완료 조건) / 영향 범위 / 참고 |
| PR | 개요(`Closes #` 이슈 연결 줄) / 주요 변경 사항 / 상세 내용 / 확인(공통 체크리스트) / 저장소별 확인 / 참고 |

- PR 공통 체크리스트: 연결된 이슈의 모든 항목이 체크됐거나 항목별 사유 댓글이 있다, Assignee와 Reviewer를 지정했다, 공개 저장소 규칙(실명·계정 ID·시크릿 없음)을 지켰다
- 저장소별 확인 예: backend 마이그레이션 파일, product-infra Terraform plan과 보호 리소스, engineering-playbook 최종 검토일
- 예외: 특정 절차 전용 이슈 템플릿(예: engineering-playbook의 모집 시즌 체크리스트)은 일반 업무용 템플릿과 따로 둠
- 모양은 이 문서가 기준. 저장소 템플릿을 바꿀 때 이 문서를 먼저 고침
