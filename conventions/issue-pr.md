# 이슈·PR 공통 규칙

이슈와 PR을 만들고, 머지하고, 닫을 때 모든 저장소에 같이 적용하는 규칙. 브랜치·커밋 원칙은 `conventions/git.md`, 머지·승인 조건은 `conventions/code-review.md`, 저장소마다 다른 값은 `conventions/repos.md`

## 제목과 이슈 연결

### 제목

| 항목 | 규칙 |
|---|---|
| 형식 | 모든 저장소의 PR·이슈 제목은 `[Type] 내용` |
| Type | 9종: `Feat`, `Fix`, `Hotfix`, `Docs`, `Refactor`, `Style`, `Test`, `Release`, `Chore`(작업 종류 라벨 9종과 같음, "라벨") |
| 영역 | Type 뒤에 영역 표기를 허용. 예: `[Feat] [서류 평가] 내용` |
| 예 | `[Feat] 로그인 API 구현` |
| 본문 | 저장소 PR 템플릿의 섹션 이름과 순서 유지("템플릿") |
| 검사 | 재사용 워크플로 repo-rule-keeper의 검사 항목. 필수 검사는 `repo-rule-keeper`("PR 검사 `repo-rule-keeper`") |

- 이유: 제목 형식을 맞춰 두면 어느 저장소에서든 목록만 보고 변경 종류를 알 수 있고, 라벨·Type 자동 지정이 제목의 `[Type]`에 의존함
- 이전 type을 9종으로 정리함: `ci`·`build`는 Chore, `perf`는 Refactor, `revert`는 Chore로 씀. `hotfix`는 커밋 type이 아니라 PR 제목에만 씀
- 커밋 메시지 형식은 저장소별로 유지함(`conventions/repos.md`, `decisions/0005-title-type-unification.md`)

### PR 제목과 이슈 연결

- PR 하나 = 이슈 하나. 항상 PR 본문(템플릿의 이슈 줄)에 `Closes #번호`를 1개만 씀
- `Closes #번호`를 쓰면 PR 화면 Development에 이슈가 자동으로 연결되고, 머지하면 이슈가 자동으로 닫힘. 손으로 연결하지 않음
- 작업이 PR 여러 개로 나뉘면 이슈를 하위 이슈(Sub-issue)로 미리 나누고 PR마다 하위 이슈 하나를 `Closes`로 닫음. 상위 이슈는 PR에 연결하지 않음. 하위 이슈가 모두 닫히고 상위 이슈 체크리스트(머지 뒤 확인 포함)가 끝나면 닫음(`tools/new-issue.sh -p 상위번호`, "체크리스트 완료와 머지·종료")
- `Refs #번호`는 쓰지 않음. Development에 연결되지 않아 PR과 이슈의 관계를 보드에서 찾을 수 없음. 예외: 릴리스(`dev` → `main`)와 hotfix PR은 이슈를 연결하지 않음
- 키워드는 `Closes`, `Fixes`, `Resolves`(대소문자 무관, 콜론 허용). 다른 저장소 이슈는 `Closes BOAZ-website/frontend#209`
- 키워드는 PR 본문이나 커밋 메시지에서만 동작함(PR 댓글은 동작하지 않음). PR을 올린 뒤 본문을 고쳐도 연결됨
- 키워드는 PR 대상이 저장소 기본 브랜치일 때만 동작함. 기능 PR은 기본 브랜치로 보냄. hotfix·릴리스 PR(`main` 대상)은 연결하지 않아도 됨. 기본 브랜치 목록은 `conventions/repos.md`

## 분류 방식

| 무엇을 나누나 | 어디에 기록 | 값 | 필수 |
|---|---|---|---|
| 작업 유형 | 이슈 Type(조직 이슈 유형) | `Feature`(기능 추가), `Bug`(오류 수정), `Task`(문서·설정·운영 작업). 기준은 "분류 기준" | 이슈 작성자 필수 |
| 프로젝트 | 조직 Project "BOAZ-website project"의 Project 필드 | 홈페이지 운영 & 유지보수, 관리자 페이지 개발, Product Management, 온보딩, Terraform Migration, SRE & 장애 대응, Design System 구축, 서비스운영팀 업무 | 이슈 작성자 필수 |
| 우선순위 | 조직 이슈 필드 Priority(이슈 사이드바 "Fields") | `Urgent`·`High`·`Medium`·`Low`. Notion의 긴급·높음·중간·낮음과 차례로 대응. 기준은 "분류 기준" | 이슈 작성자 필수 |
| 작업 종류 | 작업 종류 라벨 9종 | 아래 "라벨" | 이슈 작성자 필수, PR은 제목에서 자동 |
| 기능 영역 | 저장소 기능 라벨 | 저장소가 정함(예: backend의 `auth`, `recruitment`) | 선택 |

- 이유: 한 프로젝트가 여러 저장소에 걸침(예: 관리자 페이지 개발 = frontend_admin, backend, backend-docs). 저장소별 라벨로는 저장소마다 같은 라벨을 맞춰야 하고 한 곳에서 빠뜨리면 필터에서 빠지므로, 프로젝트는 조직 Project 필드 한 곳에서 정의함
- Project 필드 값은 Notion 티켓의 Project 속성과 같은 이름을 씀. 값을 추가·변경할 때 Notion과 함께 바꿈
- 조직 이슈 필드 중 Start date, Target date, Effort와 보드의 Size·Estimate·Iteration 필드는 쓰지 않음. 관리할 값이 늘어나 누락만 생기므로 Priority 하나만 씀
- 작업 순서와 원천
  - 개발 작업(코드·설정 변경): GitHub 이슈를 먼저 만들고 Notion 티켓을 만듦. Project·우선순위의 원천은 GitHub 이슈. Notion 티켓에는 Epic·Sprint와 이슈 링크만 적고 Project·우선순위는 다시 적지 않음(이중 입력과 불일치 방지)
  - 개발이 아닌 작업(기획, 디자인, 콘텐츠, 운영진 업무): Notion 티켓만 만듦. 원천은 Notion
  - 두 값이 다르면 원천 쪽 값으로 다른 쪽을 고침. 스프린트 시작 때 PM이 대조함
- 이유: 개발 작업은 AI로 GitHub 이슈부터 만드는 경우가 많아, 이슈를 만들 때 값을 정하면 입력이 한 번으로 끝남. 계획(Epic·Sprint)은 Notion에서 운영함

저장소 기본값(먼저 확인). 기본값이 있으면 그 값을 쓰고, 아래 판정 표 1~6은 기본값이 없는 저장소와 예외 판정에 씀

| 저장소 | 기본값 |
|---|---|
| frontend | 홈페이지 운영 & 유지보수 |
| frontend_admin, frontend_recruiting_admin | 관리자 페이지 개발 |
| design system 저장소 | Design System 구축 |
| product-infra | Terraform Migration(Phase 5 인수 판정 OPS-07 뒤에는 SRE & 장애 대응) |
| backend, backend-docs, engineering-playbook | 없음(판정 표로 판정) |

- 판정 순서(위에서부터 먼저 맞는 것): ① product-infra WBS ID가 붙은 이전 작업(OPS-07 전) → Terraform Migration ② 그 밖의 배포 워크플로·CI/CD·운영 작업 → SRE & 장애 대응 ③ 저장소 기본값 ④ 아래 판정 표 3~6
- 예: product-infra `DEP-02` 배포 롤 이전은 ①로 Terraform Migration. frontend 배포 워크플로 수정은 ②로 SRE & 장애 대응
- 이유: backend는 홈페이지·관리자 API, DB 운영, 배포를 함께 담아 한 값으로 정할 수 없음. engineering-playbook은 PM 문서와 SRE 문서가 섞임

Project 값 판정 기준(위에서부터 먼저 맞는 것)

| 순서 | 조건 | 값 |
|---|---|---|
| 1 | product-infra WBS 티켓 ID(STA, NET, IAM, STO, OBS, CMP, RDB, CDN, DEP, SEA)가 붙은 이전 작업과 이전 계획 에픽([테라폼] Migration Planning) 작업 | Terraform Migration |
| 2 | WBS 밖의 인프라 운영: 운영 서비스의 배포·CI/CD와 릴리스(라이브러리 패키지 릴리스는 규칙 3), DB 운영·업그레이드, 경보·모니터링 운영, 시즌 전환 실행, 권한 정리, 장애 기준과 절차(원복, 마감 연장, 운영 시험) | SRE & 장애 대응 |
| 3 | 제품 코드나 설정을 바꾸는 개발 작업(기능, 버그 원인 수정, 테스트, API 문서)과 그 제품의 기획(기능 명세서, WBS, IA). 운영 DB에 공고·문항을 넣는 등 개발 담당이 하는 데이터 작업 포함 | 그 제품의 값(홈페이지 운영 & 유지보수, 관리자 페이지 개발, Design System 구축) |
| 4 | 코드 변경 없이 운영진이 하는 일: 콘텐츠 정리·업로드(활동사진, 기술블로그, 수료후기, 프로젝트), 업로드 가이드 | 서비스운영팀 업무 |
| 5 | 신규 팀원 합류와 인계 자료(README, 명세 정비 등 온보딩 에픽 작업) | 온보딩 |
| 6 | 어느 프로젝트에도 속하지 않는 PM 일반 업무: 전체 일정, 프로젝트 간 우선순위 조정, 보고, 팀 전체에 적용하는 운영 규칙(R&R, 스프린트, 협업 절차·템플릿, 플레이북). 한 저장소 안의 협업 규칙·CI·템플릿 설정은 규칙 3(그 저장소 제품의 값) | Product Management |

- SRE & 장애 대응의 정의: 운영 중인 서비스를 안전하게 배포하고, 관측하고, 장애에서 복구하고, 인프라를 유지하는 일
- Product Management의 정의: 여러 프로젝트에 걸친 운영팀 전체의 계획과 관리. 분기·시즌 로드맵, 프로젝트 간 우선순위와 인력 배분, 진행 보고, 회고, 팀 운영 규칙(R&R, 스프린트, 협업 절차). 특정 제품의 기획(명세서, WBS, IA)은 그 제품 값으로 분류함
- Terraform Migration은 끝이 있는 프로젝트. OPS-07 뒤의 분류와 보관은 "새 Project 값 추가"의 종료 항목을 따름
- 한 이슈에 두 성격이 섞이면 이슈를 나누고 상위 이슈로 묶음. 장애는 원인 수정(앱 코드)은 제품 값, 탐지·복구·재발 방지 체계는 SRE & 장애 대응
- 옵션 추가·종료 절차(GitHub 옵션은 웹 화면에서만)는 "새 Project 값 추가"를 따름
- 프로젝트 값에는 기수를 넣지 않음. 기수별 작업 묶음(예: "28기 리크루팅")은 상위 이슈(Parent issue)로 만들고 하위 이슈를 연결함. Notion Epic 링크는 상위 이슈 본문에 둠
- 여러 프로젝트에 걸치는 이슈는 주된 목적의 프로젝트 하나를 고름
- backend의 `/api/v1/admin/**` API라도 관리자 콘솔 프로젝트(2026-08 시작) 이전에 홈페이지 콘텐츠·모집 운영용으로 만든 것(FAQ·커리큘럼·후기 CRUD, Admin 계정, 감사 로그, 합격자 승격 등)은 홈페이지 운영 & 유지보수. 관리자 페이지 개발은 관리자 콘솔용 기능(출결, 시스템 계정, 권한 개편, 서류 평가 앱 등)만
- 작업 유형·우선순위 기준은 이 문서 "분류 기준"(우선순위는 Notion 티켓과 같음, `org/pm-guide.md` "4. 티켓 우선순위")
- PR의 작업 종류 라벨은 제목의 `[Type]`을 보고 자동으로 붙임. 이슈는 만들 때 붙임(`tools/new-issue.sh`가 제목에서 자동 지정)

## 이슈

| 항목 | 규칙 |
|---|---|
| 담당자(Assignee) | 반드시 지정. 이슈를 만든 사람. 다른 사람이 작업을 맡으면 그 사람을 추가하거나 바꿈 |
| 작업 종류 라벨, Type | 반드시 지정. 제목 `[Type]`에 맞춤("라벨", "분류 방식") |
| Priority, Project | 반드시 지정. Priority는 조직 이슈 필드, Project는 보드 필드("분류 방식") |
| 보드 편입 | 반드시 조직 Project "BOAZ-website project"에 넣음. 권한이 없으면 PM에게 알림 |
| 만드는 방법 | AI·명령줄로 만들 때는 [`tools/new-issue.sh`](../tools/new-issue.sh)를 씀. 6개 값(Assignee, 라벨, Type, Priority, 보드 편입, Project)을 한 번에 지정하고, 하나라도 빠지면 이슈를 만들지 않음 |
| 본문 | 일반 업무 이슈 템플릿 사용. 체크리스트(`- [ ]`)로 완료 조건을 적음 |

- 이유: 담당자가 없는 이슈는 진행하는 사람 없이 남고, 유형·우선순위·프로젝트가 없으면 보드에서 급한 일을 고를 수 없음. Project 밖의 이슈는 우선순위 목록에서 보이지 않음
- GitHub은 필수 값 없이도 이슈를 만들 수 있어 생성 자체를 막지 못함. 생성 뒤 repo-rule-keeper가 검사함. 원본은 playbook의 재사용 워크플로 `.github/workflows/repo-rule-keeper.yml`(화면 표시 이름 "🛡️ repo-rule-keeper")이고, 저장소는 호출 파일 견본 [`tools/callers/repo-rule-keeper.yml`](../tools/callers/repo-rule-keeper.yml)을 `.github/workflows/repo-rule-keeper.yml`로 복사해 두며 `@v1` 태그로 고정함. 호출 파일은 이것 1개뿐이고 이슈·PR 검사가 모두 이 파일로 동작함. playbook은 로컬 호출 파일 `.github/workflows/repo-rule-keeper-run.yml`을 씀. 원본을 고치면 `v1` 태그를 옮겨 모든 저장소에 반영함
- 동작: 담당자는 작성자로, 작업 종류 라벨은 제목에서 자동으로 채우고 Type 지정도 시도함(실패하면 누락으로 알림). 이슈를 만들거나 고치거나 라벨·담당자를 바꿀 때마다 다시 검사하고(생성 직후에는 2분까지 기다림), 비어 있는 값은 마커가 붙은 댓글 1개를 갱신해 알림. 모두 채워지면 그 댓글을 "해결됨"으로 바꾸고 접음
- Priority 조회에 실패하면 누락으로 보고 job을 실패시킴(조용히 통과하지 않음). 보드 편입·Project는 저장소 권한으로 확인할 수 없어 PM 스프린트 점검에서 확인함
- 이슈를 대신 만들어 준 경우(예: 회의 결정을 PM이 이슈로 옮김)에도 만든 사람을 먼저 지정하고, 작업자가 정해지면 작업자를 추가함
- 장애 대응 예외: 운영 장애로 바로 고쳐야 하면 이슈 없이 hotfix PR을 먼저 올리고 머지할 수 있음. 복구 뒤 24시간 안에 이슈(`[Hotfix]`, Type Bug, Priority Urgent, Project SRE & 장애 대응 또는 해당 제품)를 만들어 PR 링크를 적고 닫음. 장애 절차는 `process/incident.md`

## PR

| 항목 | 규칙 |
|---|---|
| 담당자(Assignee) | 반드시 지정. PR 작성자(작업한 사람) |
| 리뷰어(Reviewer) | 반드시 지정. 작성자가 아닌 사람 1명 이상(PM 또는 해당 Product의 다른 팀원). 리뷰어가 없는 PR은 리뷰를 시작하지 않음 |
| 이슈 연결 | PR 하나 = 이슈 하나, 본문에 `Closes #번호` 1개로 Development에 연결. 여러 PR로 나뉘는 작업은 하위 이슈로 나눔. 예외: 릴리스(`dev` → `main`)와 hotfix PR은 연결하지 않음("PR 제목과 이슈 연결") |
| 작업 종류 라벨 | 제목의 `[Type]`에 맞는 라벨 1개. 자동으로 붙고, 제목을 고치면 라벨도 바뀜 |
| 본문 | PR 템플릿 사용 |

## 체크리스트 완료와 머지·종료

| 대상 | 규칙 |
|---|---|
| PR 머지 | PR 본문의 체크리스트가 모두 체크되어 있어야 머지함 |
| 이슈 종료 | 이슈 본문의 체크리스트가 모두 체크되어 있어야 닫음 |
| 체크하지 못한 항목 | 머지·종료 전에 항목마다 사유를 댓글로 남김. 형식은 `사유: <항목 문구 앞부분> / <이유>`(한 줄에 하나). 예: `사유: 엔티티 변경 여부를 확인했다 / 해당 없음, 엔티티 변경 없음`, `사유: 운영 배포 확인 / 후속 이슈 #123으로 옮김`. 사유 댓글이 있으면 머지·종료할 수 있음 |
| `Closes`로 자동 종료되는 이슈 | 리뷰어가 승인 전에 연결된 이슈를 열어 모든 항목이 체크됐거나 항목별 사유 댓글이 있는지 확인함. 일부만 처리했다면 PR을 머지하기 전에 남은 일을 하위 이슈로 나눔 |
| 머지 뒤에만 할 수 있는 확인 | 운영 배포 뒤 동작 확인처럼 머지 전에 체크할 수 없는 항목은 `Closes`로 닫히는 이슈에 넣지 않음. 상위 이슈 체크리스트에 두고, 하위 이슈가 모두 닫히고 확인이 끝나면 상위 이슈를 닫음 |
| 직접 닫는 이슈 | 닫는 사람이 같은 내용을 확인함 |

- 이유: 체크리스트는 완료 조건이므로, 체크하지 않은 채 머지·종료하면 무엇이 빠졌는지 나중에 알 수 없음
- 후속으로 미루는 항목은 후속 이슈 번호를 사유 댓글에 적음

### PR 검사 `repo-rule-keeper`

- 원본은 playbook의 재사용 워크플로 `.github/workflows/repo-rule-keeper.yml`("🛡️ repo-rule-keeper"). 저장소는 [`tools/callers/repo-rule-keeper.yml`](../tools/callers/repo-rule-keeper.yml)을 `.github/workflows/repo-rule-keeper.yml`로 복사해 `@v1`로 고정함. 결과는 커밋 상태 `repo-rule-keeper`로 기록됨
- 이 워크플로가 제목 검사(title-guard), 자동 라벨(auto-label), 작성자 자동 지정(auto-assign), 대상 브랜치 경고(pr-base-guard)를 모두 맡으므로 저장소에 이 기능의 별도 워크플로를 두지 않음
- 이슈 규칙과 PR 규칙은 잡 하나("규칙 검사")에서 이벤트에 따라 나눠 실행함. PR 검사 목록에는 워크플로 실행 "🛡️ repo-rule-keeper / rules / 규칙 검사"와 커밋 상태 `repo-rule-keeper` 두 줄이 보이며, 룰셋 필수 검사는 커밋 상태 `repo-rule-keeper`로 지정함(댓글로 다시 검사한 결과도 이 상태에 반영되기 때문)
- 실행 시점: PR을 만들거나 고칠 때, 리뷰·댓글이 달릴 때, 연결된 이슈를 고칠 때
- 검사 항목 7가지
  1. 제목 형식: `[Type] 내용`이고 Type이 9종 중 하나("제목")
  2. 라벨 자동: 제목의 `[Type]`에 맞는 작업 종류 라벨 1개만 남김(다른 작업 종류 라벨은 뗌)
  3. Assignee 자동: 비어 있으면 PR 작성자를 지정함. 지정되지 않으면 실패
  4. 대상 브랜치: 기본 브랜치가 아닌 곳을 향한 PR은 `dev`(릴리스)나 `hotfix/*` 브랜치에서 올 때만 허용함. 그 밖이면 실패로 표시함("브랜치 흐름", [git.md](git.md))
  5. `Closes` 이슈 연결: 정확히 1개. 릴리스(`[Release]`, `[Hotfix]`)와 기본 브랜치가 아닌 곳을 향한 PR은 0~1개 허용
  6. Reviewer: 지정됐거나 작성자가 아닌 사람(팀 포함)의 리뷰가 있음
  7. 사유 없는 미체크 항목이 없음: PR 본문의 미체크 항목과, `Closes` 이슈가 1개이면 그 이슈 본문의 미체크 항목. 사유는 PR 댓글이나 이슈 댓글(사람이 쓴 것만 인정)의 `사유: <항목 문구 앞부분> / <이유>` 줄로 남김. 항목 문구의 앞 30자가 사유 줄에 들어 있으면 처리된 것으로 봄
- 규칙을 어기면 상태만 `failure`가 되고, API 오류는 job 실패로 나타남. PR 본문·댓글·리뷰·이슈 본문이 바뀔 때마다 다시 검사함
- 공개 저장소는 룰셋의 필수 검사로 `repo-rule-keeper`를 지정해 머지를 막음. backend-docs(비공개)는 무료 플랜이라 룰셋을 강제할 수 없어 표시만 함(리뷰어가 상태를 확인하고 머지)

## 프로젝트 값과 저장소 추가

### 새 Project 값 추가

- 기준: "분류 방식"의 판정 표 1~6에 맞는 행이 있으면 기존 값을 씀. 새 값은 아래 셋을 모두 만족할 때만 만듦
  - 기존 정의로 판정할 수 없음
  - 이슈가 5개 이상 생길 예정
  - 기수 묶음이 아님(기수 묶음은 상위 이슈나 Notion Epic으로 만듦)
- 순서
  1. 제안 이슈(Type `Task`, Project 값 Product Management)에 값의 정의 한 줄과 판정 표에 넣을 행을 적음
  2. PM이 승인함
  3. 변경 전 기존 배정을 내보냄(이슈 번호와 Project 값 목록을 저장)
  4. Notion 두 DB(Engineering Ticket, 디자인 & FE Ticket)와 GitHub 조직 Project에 같은 이름으로 옵션을 추가함. GitHub 옵션은 웹 화면에서만 추가하고, 기존 옵션은 지우거나 이름을 바꾸지 않음
  5. 세 곳에 옵션이 생긴 것을 확인한 뒤 이 문서의 판정 표와 정의를 고치는 PR을 머지함
  6. 기존 티켓을 판정 표로 다시 분류함
- 중간에 멈추면 어디까지 했는지 제안 이슈 댓글에 기록함
- 이유: API로 옵션 목록을 덮어쓰면 기존 값이 지워질 수 있음(2026-11 실제로 발생). 그래서 3단계에서 배정을 내보내 둠
- 종료(보관): 옵션을 삭제하지 않고 세 곳에 남김. 정의에 "신규 사용 중단일"과 "이후 작업을 넘길 값"을 적고, 판정 표에서 그 행에 종료 표시를 함. 다른 값과 합치지 않음(이전 이력 보존)
- Terraform Migration은 OPS-07 뒤 WBS ID가 붙은 후속 작업도 SRE & 장애 대응으로 분류함(종료 기준이 규칙 1보다 우선)

### 새 저장소 추가

체크리스트는 `conventions/repos.md` "새 저장소 추가"에 있음([repos.md](repos.md))

### 필수 값과 누락 점검

- 이슈 작성자 필수 값은 Assignee, 작업 종류 라벨, Type, Priority, 보드 편입, Project("이슈" 절)
- Notion 티켓 필수 값: 개발 티켓은 Epic, Sprint, GitHub Issue 링크. 개발이 아닌 티켓은 Epic, Sprint, Project, 우선순위
- 누락 점검: 스프린트 시작 때 PM이 확인함
  - 핵심: 저장소별 `is:issue is:open no:project` 검색. 보드 밖 이슈는 보드 안 빈 값 뷰에 보이지 않고, 자동 편입 규칙은 1개 저장소만 대상이므로 이 검색이 필요함
  - 보드 안: Project가 빈 항목 뷰. Priority는 조직 이슈 필드라 보드 밖 이슈도 저장소 이슈 검색으로 빈 값을 찾음
  - Notion 두 DB: 개발 티켓 중 GitHub 링크가 없는 것, 개발이 아닌 티켓 중 Project가 빈 것
  - 반대 방향: 이번 스프린트에 열린 GitHub 이슈 중 Notion 티켓에 링크되지 않은 것(이슈만 만들고 티켓을 빠뜨린 경우)
  - 대조: 이번 스프린트 Notion Ticket의 Project·우선순위와 연결 이슈의 GitHub 값을 대조하고, 다르면 원천 쪽 값으로 고침(개발 작업은 GitHub, 그 밖은 Notion)
  - repo-rule-keeper의 누락 알림 댓글이 달린 이슈
- 빈 값 필터는 저장 뷰로 만들어 둠
- 이유: Project 값이 비면 프로젝트 필터 화면에서 빠져 누락을 알아채기 어려움

## 분류 기준

### 작업 종류 라벨과 Type

| 제목 접두어 | 라벨 | Type | 언제 쓰나 | 애매할 때 예 |
|---|---|---|---|---|
| `[Feat]` | `⭐️ FEAT` | `Feature` | 사용자·운영진이 쓸 수 있는 기능이 새로 생기거나 바뀜 | API 필드 추가·화면 추가는 Feat. 기존 기능 문구만 바꾸면 Fix 또는 Style |
| `[Fix]` | `🐛 FIX` | `Bug` | 의도와 다르게 동작하던 것을 고침(설정값 오류 포함) | 잘못된 환경 변수 값 수정은 Fix, 새 환경 변수 추가는 Chore |
| `[Hotfix]` | `🚑 HOTFIX` | `Bug` | 운영 중 장애·모집 차단을 main에서 바로 고침(`process/incident.md`) | 운영 영향이 없으면 Fix |
| `[Docs]` | `✏️ DOCS` | `Task` | 문서·주석·README·명세만 바꿈 | 코드와 문서를 함께 바꾸면 코드 쪽 접두어 |
| `[Refactor]` | `🛠️ REFACTOR` | `Task` | 동작 변경 없는 구조 개선 | 성능 개선도 동작이 같으면 Refactor |
| `[Style]` | `🧁 STYLE` | `Task` | 포맷팅·린트·UI 미세 조정처럼 동작 변경 없음 | 화면 배치가 바뀌어 사용 흐름이 달라지면 Feat |
| `[Test]` | `🔎 TEST` | `Task` | 테스트 코드만 추가·수정 | 버그 수정과 그 테스트는 Fix 하나 |
| `[Release]` | `🚀 RELEASE` | `Task` | `dev` → `main` 릴리스 PR(이슈 없음) | - |
| `[Chore]` | `🧹 CHORE` | `Task` | 빌드·CI·의존성·설정·저장소 관리 | 의존성 버전 올리기, 워크플로 추가는 Chore. 배포 파이프라인 변경의 Project 값은 "분류 방식"의 판정 순서를 따름 |

- 제목 접두어 하나로 라벨과 Type이 함께 정해짐(`tools/new-issue.sh`, repo-rule-keeper가 같은 대응을 씀)
- repo-rule-keeper의 이슈 규칙은 라벨은 자동으로 붙이지만 Type은 저장소 토큰 권한이 없어 지정에 실패하고 누락 댓글로 알림(2026-11-28 시험, playbook #47, 기존 기록 유지)
- 두 성격이 섞이면 주된 변경 하나를 고르고, 크면 하위 이슈로 나눔

### Priority

- 4단계 하나만 씀. GitHub 조직 이슈 필드 값과 Notion 값 대응: Urgent=긴급, High=높음, Medium=중간, Low=낮음

| GitHub | Notion | 기준 | 처리 | 예 |
|---|---|---|---|---|
| `Urgent` | 긴급 | 심각도 높음 장애, 모집·운영이 막힘(`process/incident.md` 심각도 기준과 같음) | 즉시 착수, 다른 일보다 먼저 | 접수 기간 중 지원서 제출 오류, 운영 서버 다운 |
| `High` | 높음 | 이번 스프린트 목표 | 이번 스프린트 안에 끝냄 | 접수 시작 전 공고 반영, 스프린트 목표 기능 |
| `Medium` | 중간 | 다음 스프린트 대상 | 다음 스프린트 계획 때 배정 | 운영에 영향 없는 버그, 개선 작업 |
| `Low` | 낮음 | 여유가 있을 때 | 기한 없음 | 리팩터링, 문서 보완 |

- 높음과 중간 사이에서 애매하면 중요성(목표·사용자 영향)과 시급성(기한)을 함께 봄. 둘 다 높으면 High, 하나만 높으면 Medium. 아래 보조 표로 판단함

높음과 중간 사이를 판단할 때 쓰는 보조 표

| 우선순위 | 중요성 | 시급성 | 처리 |
|---|---|---|---|
| 높음(High) | 높음 | 높음 | 이번 스프린트 안에 끝냄. 지연 시 프로젝트 전반 영향 |
| 중간(Medium) | 높음 | 낮음·중간 | 다음 스프린트 계획 때 배정 |
| 중간(Medium) | 낮음·중간 | 높음 | 빠른 해결 필요. 일정 영향 방지 |
| 낮음(Low) | 낮음 | 낮음 | 여유가 있을 때 처리 |

- 긴급(Urgent)은 이 표로 정하지 않음. 장애·모집 차단일 때만 씀
- 방법: 작업마다 중요성과 시급성을 보고 표에서 같은 조합의 우선순위를 찾음. 둘 다 높으면 높음, 둘 다 낮으면 낮음, 그 밖의 조합(하나만 높음, 둘 다 중간 등)은 중간
- 최종 결정은 PM. 스프린트 중 긴급 장애가 생기면 Urgent로 올리고 PM에게 바로 알림

| 템플릿 | 섹션(순서 고정) |
|---|---|
| 이슈 | 작업 내용(무엇을 왜) / 작업 상세 내용(체크리스트, 완료 조건) / 참고 |
| PR | 개요(`Closes #` 이슈 연결 줄) / 주요 변경 사항 / 상세 내용 / 확인(공통 체크리스트) / 저장소별 확인 / 참고 |

- 원본 위치: playbook의 `.github/`(playbook 자신이 쓰는 파일)와 [`tools/templates/`](../tools/templates/)(다른 저장소용 견본: `task.yml`, `config.yml`, `PULL_REQUEST_TEMPLATE.md`). 저장소는 견본을 복사해 쓰고, 원본을 고치면 각 저장소 복사본을 함께 고침
- 일반 이슈는 이슈 폼 `task.yml`로 만듦. 빈 이슈는 만들 수 없게 `config.yml`에서 막음(`blank_issues_enabled: false`)
- PR 공통 체크리스트: Closes 1개로 이슈를 연결했다, Assignee와 Reviewer를 지정했다, 연결된 이슈의 체크리스트를 완료했거나 항목별 사유 댓글이 있다
- 저장소별 확인 예: backend 마이그레이션 파일, product-infra Terraform plan과 보호 리소스, engineering-playbook 최종 검토일·결정 기록·문서 간 어긋남·공개 저장소 확인(실명·계정 ID·시크릿 없음). 견본에는 `해당 없음(저장소별 항목으로 바꿈)`으로 두고 저장소가 바꿈
- 예외: 특정 절차 전용 이슈 템플릿(예: engineering-playbook의 모집 시즌 체크리스트)은 일반 업무용 이슈 폼과 따로 둠
- 모양은 이 문서가 기준. 저장소 템플릿을 바꿀 때 이 문서를 먼저 고침
