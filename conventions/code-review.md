# 코드 리뷰 규칙

## 규칙

| 항목 | 규칙 |
|---|---|
| 리뷰어 수 | PR당 작성자 외 1명 이상 승인 |
| 머지 조건 | 승인 1건 이상, 필수 검사 통과, 대화 모두 해결 |
| 승인 전 머지 | 금지 |
| 작성자 단독 머지 | 금지. 작성자는 자신의 PR을 승인하지 않음 |
| 새 커밋 | 승인 후 새 커밋이 올라오면 기존 승인 무효화 |
| PR 없이 병합 | 금지. 문서만 바뀌어도 PR 사용 |
| 머지 방식 | merge commit. 승인과 필수 검사 `repo-rule-keeper` 통과를 확인한 뒤 머지(현황: 5개 저장소는 merge commit으로 머지 중이고, design-system 외 4개는 설정에서 squash·rebase도 허용 상태) |

- 근거: 팀 Notion의 FE 리뷰 규칙(머지 승인 1명)과 frontend_admin 보호 설정 제안 기본값 일치
- 브랜치 보호 설정 반영: 저장소 관리자(권한은 `org/roles-and-authority.md`)

왜 이렇게 하는지

- 작성자 외 1명 이상이 확인해야 작성자가 놓친 문제를 발견할 수 있음
- 승인 후 새 커밋이 올라오면 승인은 이전 코드에 대한 것이므로 무효화함
- 문서만 바뀌어도 PR을 쓰면 모든 변경에 기록과 리뷰가 남음

구체적으로 어떻게 하는지

- 작성자는 자신의 PR을 승인하지 않고, 리뷰어의 승인 1건 이상과 필수 검사 통과, 모든 대화 해결을 확인한 뒤 머지함

## 응답 기준

| 항목 | 기준 |
|---|---|
| 첫 응답 | 평일 기준 2일 이내. hotfix PR은 당일 |
| 리뷰어 지정 | 작성자가 PR 생성 시 반드시 지정. 작성자가 아닌 사람 1명 이상(PM 또는 해당 Product의 다른 팀원). 지정과 담당자 규칙은 `conventions/issue-pr.md` |
| 응답 지연 시 | PM에게 알리고 리뷰어 재지정. 셀프 머지 금지 |
| 수정 요청 | 해결될 때까지 승인하지 않음 |
| 재검토 | 작성자가 반영 후 리뷰어에게 재요청 |

- 근거 제시: 의견에 참고 자료 첨부
- 코멘트 강도: 코멘트 머리말 2단계. 리뷰 기한 라벨(D-n)은 쓰지 않고 위 응답 기준을 따름

| 머리말 | 의미 |
|---|---|
| `[필수]` | 머지 전 반영 |
| `[제안]` | 반영 여부는 작성자 판단 |

- 머리말 없는 코멘트는 `[제안]`으로 봄
- 어투: 정중하게 작성. 사람이 아닌 코드에 대한 의견으로 기재

왜 이렇게 하는지

- 응답 기한을 정해 두어야 리뷰 대기로 작업이 멈추지 않고, 지연되어도 셀프 머지 대신 리뷰어를 바꿔 해결함

구체적으로 어떻게 하는지

- 작성자는 PR을 올릴 때 리뷰어를 지정함. 지정하지 않으면 PM이 지정함
- 리뷰어가 기한 안에 응답하지 않으면 작성자가 PM에게 알리고, PM이 리뷰어를 다시 지정함
- 수정 요청을 받으면 반영한 뒤 리뷰어에게 재검토를 요청함

## 작은 PR

| 항목 | 기준 |
|---|---|
| 범위 | PR 1건 = 이슈 1건 = 변경 목적 1가지(연결 방법은 `conventions/issue-pr.md` "PR 제목과 이슈 연결") |
| 크기 | 변경 400줄 권장 상한. 넘으면 PR 본문에 이유를 적음. 자동 생성 파일(`schema.d.ts`, `dist/`, 잠금 파일)은 줄 수에서 제외. 차단 기준이 아닌 권장 기준 |
| 분할 | 큰 작업은 하위 이슈로 나누고 하위 이슈마다 PR 1건으로 분할(`conventions/issue-pr.md` "PR 제목과 이슈 연결") |
| 제외 | 포맷 변경, 파일 이동은 기능 변경과 같은 PR에 섞지 않음 |
| 설명 | PR 본문은 자세히. 문제, 해결 방식, 확인 방법 기재 |

- 왜: 변경이 작고 목적이 하나여야 리뷰어가 한 번에 파악할 수 있고, 포맷 변경이 섞이면 기능 변경이 가려짐
- 방법: 400줄을 넘을 것 같으면 먼저 하위 이슈로 나누고 하위 이슈마다 PR을 하나씩 올림. 나눌 수 없으면 PR 본문에 넘은 이유를 적음. 이 크기는 권장 기준이며 머지를 막지 않음

## 초안 PR

| 항목 | 규칙 |
|---|---|
| 사용 시점 | 작업 중 방향 확인, 이른 피드백이 필요할 때 |
| 머지 | 초안 상태에서는 머지 불가. 준비되면 일반 PR로 전환 |
| 리뷰 요청 | 초안 PR은 리뷰 의무 없음. 요청한 경우만 응답 |
| 검사 | 초안 PR에도 CI 실행(frontend_admin 규칙) |

- 왜: 완성 전에 방향을 먼저 확인하면 큰 수정이 뒤늦게 필요해지는 일을 줄일 수 있음
- 방법: 초안 PR로 올려 리뷰어에게 요청한 경우에만 의견을 받고, 준비되면 일반 PR로 전환해 정식 리뷰를 받음

## 리뷰어 확인 항목

| 구분 | 확인 |
|---|---|
| 동작 | 이슈 요구사항 충족, 테스트 통과 |
| 일관성 | 저장소 코드 스타일, 이름 규칙 |
| 위험 | 성능, 보안, 시크릿 포함 여부 |
| 이슈 TO-DO | 연결된 이슈의 체크 상태와 PR 내용 일치(`conventions/issue-pr.md` "체크리스트 완료와 머지·종료") |
| 연동 | API 변경이면 프론트엔드 영향, DB 변경이면 마이그레이션 파일 |
| 문서 | 공개 저장소 규칙 위반 여부(`conventions/doc-writing.md`) |

- 방법: 리뷰어는 이 표를 순서대로 확인하고, 문제가 있으면 코드에 대한 의견으로 근거와 함께 남김
- 이유: 저장소가 공개라 시크릿이나 내부 정보가 올라가면 회수하기 어려워 리뷰에서 한 번 더 확인함

## 채택하지 않는 기존 규칙

| 기존 규칙 | 사유 |
|---|---|
| 리뷰가 지연되면 작성자 책임으로 직접 머지 | 승인 전 머지 금지 원칙과 충돌 |
| 간단한 수정은 구두 상의 후 PR 없이 병합 | 변경 기록과 리뷰 누락 |
| main 대상 승인 2명, dev 대상 승인 1명 | 전체 인원 4명(PM 1명, Product Engineer 3명) 체계에서 2명 승인은 작성자 외 인원 부담이 큼. 재검토 조건은 아래 참조 |

- 재검토 조건: main 대상 PR에서 리뷰 누락으로 인한 장애가 발생하면 main 승인 수 상향 검토
- 이 규칙의 변경은 결정 기록 추가가 필요

## 미결

| 질문 | 결정 필요 주체 | 필요 시점 |
|---|---|---|
| 릴리스 PR(dev→main) 승인 수 | PM | 공용 검사 도입 전 |
| 머지 방식을 merge commit으로 확정하고 squash·rebase 허용 설정을 끌지 | PM | 저장소별 전환 전 |
