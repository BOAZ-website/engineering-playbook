# 배포 순서

이 문서가 상세 기준. `process/release.md`의 "백엔드와 프론트엔드 배포 순서"는 이 문서의 요약

## 결정 사항

| 항목 | 규칙 |
|---|---|
| 기본 순서 | 백엔드를 먼저 배포하고 프론트엔드를 그다음에 배포 |
| 호환되는 변경 | 백엔드 먼저, 프론트엔드 나중 |
| 호환되지 않는 변경 | 3단계로 나눔. 한 번의 배포로 바꾸지 않음 |

- 근거: 프론트엔드가 먼저 나가면 아직 없는 필드를 요청하거나 읽어 화면 오류가 발생
- 근거: 두 배포 사이에는 시간 차가 있어 한 번에 바꾸면 그 사이에 구버전과 신버전이 섞임

## 변경 분류

| 분류 | 예 | 순서 |
|---|---|---|
| 호환되는 변경 | 응답 필드 추가, 선택 요청 필드 추가 | 백엔드 배포 → 프론트엔드 타입 재생성·배포 |
| 호환되지 않는 변경 | 필드 삭제, 이름 변경, 타입 변경 | 아래 3단계 |

## 호환되는 변경 절차

| 순서 | 작업 | 담당 |
|---|---|---|
| 1 | 백엔드 `dev` 머지 | Product Engineer |
| 2 | 프론트엔드 타입 재생성 후 PR | Product Engineer |
| 3 | 백엔드 릴리스·배포 확인 | Product Engineer |
| 4 | 프론트엔드 릴리스 | Product Engineer |

## 호환되지 않는 변경 3단계

| 단계 | 작업 | 완료 조건 |
|---|---|---|
| 1 | 백엔드에 새 필드 추가 배포. 옛 필드 유지 | 새·옛 필드가 모두 응답에 포함 |
| 2 | 프론트엔드가 새 필드로 전환해 배포 | 프론트엔드가 옛 필드를 읽지 않음 |
| 3 | 백엔드에서 옛 필드 삭제 배포 | 응답에 옛 필드 없음 |

- 단계 3은 단계 2 배포 확인 후에 수행
- 단계 3 전에 구버전 프론트엔드가 캐시에 남아 있을 가능성 확인 (2026-11-25 기준 frontend 배포 워크플로는 S3 동기화 뒤 CloudFront 캐시를 전체 경로(`/*`)로 무효화함. 동기화 명령에 `Cache-Control` 지정 없음. frontend_admin 저장소에는 배포 워크플로 없음) [확인 필요: 관리자 페이지 배포·캐시 정책]
- 관리자 페이지가 백엔드와 연동된 뒤에는 관리자 페이지도 단계 2에 포함

## 시즌 전환과 겹칠 때

- 시즌 전환 전날부터 전환 결과 확인까지 릴리스 금지, hotfix만 허용
- DB 스키마 변경이 든 릴리스는 시즌 전환과 같은 주에 하지 않음
- 상세: `process/release.md`
