# 0001 Git 규칙 통일

## 상태

| 항목 | 값 |
|---|---|
| 상태 | 채택 |
| 결정일 | 2026-11-24 |
| 결정 주체 | PM |

## 배경

- 저장소마다 커밋·브랜치·PR 제목 규칙이 달라 5개 Product를 오가는 Product Engineer가 저장소마다 규칙을 따로 기억해야 함
- 현황 상세는 `conventions/git.md`의 저장소별 현황 표
- 규칙 안내 문서끼리도 어긋남(예: 브랜치 예시에 `#` 포함 여부, 허용 type 수)

## 선택지

| 선택지 | 내용 | 채택 | 탈락 사유 |
|---|---|---|---|
| A | 저장소별 규칙 유지 | 아니오 | 5개 Product 전체를 다루는 체계와 맞지 않음 |
| B | 한 저장소의 규칙을 전체에 적용 | 아니오 | 저장소마다 허용 type과 PR 제목 형식이 달라 어느 쪽도 다른 저장소와 일치하지 않음 |
| C | 공통 기준을 새로 정하고 `.github` 공용 검사로 확인 | 예 | 해당 없음 |

## 결정

- 커밋·PR 제목·브랜치·브랜치 흐름을 아래 기준으로 통일함

| 항목 | 기준 |
|---|---|
| 커밋 | `type: 설명 (#이슈번호)`. type은 feat fix docs style refactor test chore ci build perf revert |
| PR 제목 | `[Type] 내용` |
| 브랜치 | `type/이슈번호-짧은-설명`. 예: `feat/12-login-api`. `#` 미사용 |
| 기본 흐름 | 기능 브랜치 → `dev` → `main` |
| hotfix | `main`에서 `hotfix/*` 분기 → `main`으로 PR → 머지 후 `dev`에 역머지 |

적용 방식

- 기존 커밋 기록은 수정하지 않음. 적용 기준일부터 적용
- 적용 순서: playbook 공개 → `.github` 공용 검사(경고만) → 저장소별 전환 → 전환 2주 뒤 차단
- 다른 저장소 적용은 2026-12 리크루팅 시즌 이후

- `main` 진입 경로 제한(2026-11-24 PM 확정): `main`에 들어가는 변경은 `dev` → `main` 릴리스 PR과 `hotfix/*` → `main` PR뿐임. 그 밖의 브랜치에서 올리는 PR과 직접 push는 차단함. `release/*` 브랜치는 쓰지 않음. hotfix 머지 뒤에는 같은 브랜치로 `dev` 대상 PR을 올려 역머지함. PR 제목에는 `[Hotfix]`, `[Release]`를 추가로 허용하고 커밋 type에는 넣지 않음
- 머지 방식은 merge commit(5개 저장소의 현재 방식)

## 근거

- 커밋 형식 `type: 설명 (#이슈번호)`는 backend, product-infra, frontend_admin에서 이미 사용 중이라 전환 비용이 가장 작음
- 11종 type은 frontend_admin의 허용 목록과 같고 backend 훅의 7종을 포함함
- 브랜치에서 `#` 제거: 셸에서 `#` 이후가 주석으로 처리되어 명령마다 따옴표가 필요함(frontend_admin 문서에 따옴표 안내 존재)
- 이슈 번호가 커밋·브랜치·PR에 모두 있어야 이슈와 변경이 연결됨
- 경고 단계를 먼저 둬서 시즌 중 작업 차단을 피함
