# 장애 대응

절차만 기록. 명령어, 로그 위치, 호스트명, 콘솔 위치는 비공개 운영 문서 참조

## 결정 사항

| 항목 | 규칙 |
|---|---|
| 우선 원칙 | 원인 분석보다 되돌리기를 먼저 수행 |
| 보호 리소스 | RDS, S3, CloudFront는 승인 없이 변경 금지 |
| 시즌 전환 중 장애 | PM에게 즉시 알림 |
| 회고 | 비난 없이 작성. 공개 문서에는 일반화해서 기록 |

- 근거: 사용자 영향 시간이 복구 속도에 비례하고, 원인 분석은 복구 후에도 가능
- 근거: 보호 리소스 변경은 데이터 손실 위험이 있어 승인 필요

## 심각도

| 단계 | 정의 | 대응 시한 | 사용자 공지 |
|---|---|---|---|
| 높음 | 서비스 전체 중단, 데이터 손상 위험, 보안 문제 | 발견 후 1시간 안에 착수. 모집 기간(서류 모집 시작~마감)에는 30분 안. 4시간 안에 완화 목표 | 필요 |
| 중간 | 일부 기능 중단 또는 성능 저하로 사용자 영향 있음 | 24시간 안에 착수. 모집 기간에는 당일 | 영향이 30분 이상이면 필요 (추정) |
| 낮음 | 사용자 영향 없음. 경보만 발생 | 다음 업무일 | 불필요 |

- 심각도 판단이 불명확하면 한 단계 높게 분류
- 심각도 변경은 대응 담당이 결정하고 기록

## 역할

| 역할 | 담당 업무 |
|---|---|
| 대응 담당 | 확인, 완화, 복구 수행. Product Engineer |
| 소통 담당 | 상황 공유, 사용자 공지 초안, 대표진 소통. PM |

- 대응 담당 지정: PM이 접수 시 지정
- 한 명이 두 역할을 겸하지 않음. 인원이 부족하면 PM이 겸임하고 기록
- 복구 작업 권한이 필요하면 `org/access.md`의 권한 보유자에게 요청

## 단계

| 단계 | 작업 | 완료 조건 |
|---|---|---|
| 접수 | 경보 또는 제보 수신. 심각도 분류. 대응 담당 지정 | 이슈 생성 |
| 확인 | 영향 범위와 시작 시각 파악. 최근 배포·변경 여부 확인 | 영향 범위 기록 |
| 완화 | 직전 배포 되돌리기 등 영향 축소 | 사용자 영향 감소 확인 |
| 복구 | 정상 상태 회복 확인 | 경보 해소, 주요 기능 점검 |
| 회고 | 원인, 대응, 재발 방지 정리 | 회고 기록 머지 |

### 장애 종료 조건

아래 세 가지를 모두 충족해야 장애를 종료함. 대응 담당이 이슈에 세 항목의 근거를 적고 종료를 선언함

| 조건 | 확인 내용 |
|---|---|
| 원인 파악 | 장애를 일으킨 원인을 찾아 이슈에 기록함 |
| 수정 반영 | 원인을 고친 변경이 운영에 배포됨. 되돌리기만 한 상태는 해당하지 않음 |
| 정상 동작 확인 | 사용자 쪽에서 영향받은 기능이 정상 동작하는 것을 직접 확인함. 경보 해소만으로는 부족함 |

- 임시 조치(되돌리기, 재시작)로 영향만 줄인 상태에서 종료하면, 원인이 남아 같은 장애가 다시 날 수 있음
- 원인을 바로 찾지 못하면 장애를 열어 둔 채 "완화" 상태로 기록하고, 원인 조사를 후속 작업으로 남김

- 되돌리기 방법: Product별 문서의 "배포와 되돌리기"(`products/`)
- 구체 명령과 위치: 비공개 운영 문서 참조
- 복구 불가 시 DB 시점 복원은 인프라 작업 권한 보유자가 수행. 복원 시각 이후 데이터가 사라지므로 PM 승인 필요
- 시급한 코드 수정은 hotfix 절차(`process/release.md`)

## 사용자 공지 기준

| 조건 | 공지 |
|---|---|
| 심각도 높음 | 필요. PM이 승인 |
| 모집 시즌 중 지원·접수 기능 중단 | 심각도와 무관하게 필요 |
| 데이터 유출 가능성 | 필요. PM이 공지 범위 결정 |
| 사용자 영향 없음 | 불필요 |

- 공지 문구는 소통 담당이 작성하고 PM이 승인
- 홈페이지 장애 공지: PM이 공지 초안을 쓰고 대표진이 동아리 공식 채널에 게시
- 장애 중에는 웹사이트 배너를 띄울 수 없으므로 외부 채널을 사용
- 모집 마감 연장 여부는 대표진이 결정

## 시즌 전환 중 장애

| 순서 | 작업 |
|---|---|
| 1 | PM에게 즉시 알림 |
| 2 | 전환 작업 중단 여부는 PM이 결정 |
| 3 | 전환 이슈에 장애 내용 기록 |

- 전환 일정과 겹친 릴리스는 중단. hotfix만 허용(`process/release.md`)

## 운영 변경 기록

| 항목 | 내용 |
|---|---|
| 기록 대상 | 장애 대응 중 수행한 설정 변경, 되돌리기, 복원 |
| 기록 위치 | 해당 이슈의 댓글 |
| 기록 항목 | 변경 일시(절대 날짜), 변경 내용 요약, 수행 역할, 결과 |
| 식별자 | 자원 ID, 계정 ID, 주소는 공개 이슈에 적지 않음. 비공개 운영 문서에 기록 |

## 회고 기록 원칙

- 사람이 아닌 절차와 구조를 대상으로 작성. 책임 소재 서술 금지
- 사실과 대응만 기재. 시각은 절대 날짜로 기록
- 공개 문서에는 일반화해서 작성. 자원 ID, 호스트명, 내부 링크, 개인 정보 제외
- 상세 기록은 비공개 위치에 보관
- 재발 방지 액션은 담당 역할, 기한(절대 날짜), 완료 조건을 가진 이슈로 등록
- 규칙 자체를 바꾸는 경우 결정 기록 작성(`decisions/`)

## 사후 분석 작성 조건과 양식

다음 중 하나에 해당하면 사후 분석(postmortem)을 작성함

| 조건 |
|---|
| 사용자가 체감한 장애 |
| 데이터 유실 위험이 있었던 장애 |
| 되돌리기를 수행한 경우 |
| 경보가 아니라 사람이 먼저 발견한 경우 |

| 양식 항목 | 내용 |
|---|---|
| 요약 | 무슨 일이 있었는지 2~3줄 |
| 영향 범위·시간 | 영향받은 기능·사용자 범위, 시작·종료 시각(절대 날짜) |
| 타임라인 | 발생, 접수, 완화, 복구 시각과 수행한 작업 |
| 원인 | 직접 원인과 그것을 막지 못한 절차·구조 |
| 잘한 점 | 효과가 있었던 대응 |
| 개선할 점 | 늦었거나 부족했던 부분 |
| 후속 작업과 담당 역할 | 이슈로 등록. 담당 역할, 기한, 완료 조건 |

- 작성 원칙은 위 "회고 기록 원칙"을 따름
