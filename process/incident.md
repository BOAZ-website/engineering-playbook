# 장애 대응

절차만 기록. 명령어, 로그 위치, 호스트명, 콘솔 위치는 비공개 운영 문서 참조

## 결정 사항

| 항목 | 규칙 |
|---|---|
| 우선 원칙 | 원인 분석보다 되돌리기를 먼저 수행 |
| 보호 리소스 | RDS, S3, CloudFront는 승인 없이 변경 금지 |
| 시즌 전환 중 장애 | PM에게 즉시 알림 |
| 회고 | 비난 없이 작성. 공개 문서에는 일반화해서 기록 |

- 근거: 사용자 영향 시간이 복구 속도에 비례하고, 원인 분석은 복구 후에도 가능
- 근거: 보호 리소스 변경은 데이터 손실 위험이 있어 승인 필요

## 심각도

| 단계 | 정의 | 대응 시한 | 사용자 공지 |
|---|---|---|---|
| 높음 | 서비스 전체 중단, 데이터 손상 위험, 보안 문제 | 발견 후 1시간 안에 착수. 모집 기간(서류 모집 시작~마감)에는 30분 안. 4시간 안에 완화 목표 | 필요 |
| 중간 | 일부 기능 중단 또는 성능 저하로 사용자 영향 있음 | 24시간 안에 착수. 모집 기간에는 당일 | 영향이 30분 이상이면 필요 (추정) |
| 낮음 | 사용자 영향 없음. 경보만 발생 | 다음 업무일 | 불필요 |

- 심각도 판단이 불명확하면 한 단계 높게 분류
- 심각도 변경은 대응 담당이 결정하고 기록

## 역할

| 역할 | 담당 업무 |
|---|---|
| 대응 담당 | 확인, 완화, 복구 수행. Product Engineer |
| 소통 담당 | 상황 공유, 사용자 공지 초안, 대표진 소통. PM |

- 대응 담당 지정: PM이 접수 시 지정
- 한 명이 두 역할을 겸하지 않음. 인원이 부족하면 PM이 겸임하고 기록
- 복구 작업 권한이 필요하면 `org/access.md`의 권한 보유자에게 요청

## 단계

| 단계 | 작업 | 완료 조건 |
|---|---|---|
| 접수 | 경보 또는 제보 수신. 심각도 분류. 대응 담당 지정 | 이슈 생성 |
| 확인 | 영향 범위와 시작 시각 파악. 최근 배포·변경 여부 확인 | 영향 범위 기록 |
| 완화 | 직전 배포 되돌리기 등 영향 축소 | 사용자 영향 감소 확인 |
| 복구 | 정상 상태 회복 확인 | 경보 해소, 주요 기능 점검 |
| 회고 | 원인, 대응, 재발 방지 정리 | 회고 기록 머지 |

### 장애 종료 조건

아래 세 가지를 모두 충족해야 장애를 종료함. 대응 담당이 이슈에 세 항목의 근거를 적고 종료를 선언함

| 조건 | 확인 내용 |
|---|---|
| 원인 파악 | 장애를 일으킨 원인을 찾아 이슈에 기록함 |
| 수정 반영 | 원인을 고친 변경이 운영에 배포됨. 되돌리기만 한 상태는 해당하지 않음 |
| 정상 동작 확인 | 사용자 쪽에서 영향받은 기능이 정상 동작하는 것을 직접 확인함. 경보 해소만으로는 부족함 |

- 임시 조치(되돌리기, 재시작)로 영향만 줄인 상태에서 종료하면, 원인이 남아 같은 장애가 다시 날 수 있음
- 원인을 바로 찾지 못하면 장애를 열어 둔 채 "완화" 상태로 기록하고, 원인 조사를 후속 작업으로 남김

- 되돌리기 방법: Product별 문서의 "배포와 되돌리기"(`products/`)
- 구체 명령과 위치: 비공개 운영 문서 참조
- 복구 불가 시 DB 시점 복원은 인프라 작업 권한 보유자가 수행. 복원 시각 이후 데이터가 사라지므로 PM 승인 필요
- 시급한 코드 수정은 hotfix 절차(`process/release.md`)

## 대응 인원

- 장애 대응은 서비스운영팀 팀원 전원이 함. 별도 당직 순번을 두지 않음
- 경보나 제보를 먼저 본 팀원이 팀 메신저에 알리고 대응을 시작함. 야간·휴일도 같음
- 원인 영역의 담당(인프라, 백엔드, 프론트)이 이어받고, PM 승인이 필요한 작업(복원, 공지)은 PM에게 요청함

## 사용자 공지 기준

| 조건 | 공지 |
|---|---|
| 심각도 높음 | 필요. PM이 승인 |
| 모집 시즌 중 지원·접수 기능 중단 | 심각도와 무관하게 필요 |
| 데이터 유출 가능성 | 필요. PM이 공지 범위 결정 |
| 사용자 영향 없음 | 불필요 |

- 공지 문구는 소통 담당이 작성하고 PM이 승인
- 홈페이지 장애 공지: PM이 공지 초안을 쓰고 대표진이 동아리 공식 채널에 게시
- 장애 중에는 웹사이트 배너를 띄울 수 없으므로 외부 채널을 사용
- 모집 마감 연장 여부는 대표진이 결정
- 연장 기준과 수행 방법은 시즌 시작 전에 정함. 시즌 판단자가 요청하고 수행을 확인함(`process/recruiting-season.md`의 REL-07)

## 계획된 운영 시험

경보 도착 시험, 부하 테스트, 장애 대응 훈련처럼 운영 환경에서 미리 계획해 하는 시험의 공지·실행·종료 규칙

- 원칙: 공지되지 않은 경보는 실제 장애로 봄. 시험은 사전 공지 없이 시작하지 않음
- 근거: 당직 없이 경보를 먼저 본 팀원이 대응을 시작하므로("대응 인원"), 공지 없는 시험은 불필요한 대응을 부르거나 실제 경보를 시험으로 오인하게 함

### 시험 등급

| 등급 | 대상 | 절차 | 모집 기간(서류 모집 시작 2일 전 ~ season-down 완료) |
|---|---|---|---|
| A 공지만 | 경보 도착 시험(경보 상태 강제 변경), 운영을 바꾸지 않는 읽기 확인, 시험용 DB 복원 시험(운영 DB 미접촉) | 공지 후 수행 | 공지 후 가능 |
| B 공지 + PM 승인 | 부하 테스트, 장애 대응 훈련(설정 변경·되돌리기 포함), 운영에서 시험 계정으로 하는 제출·발송 시험 | PM 승인 후 공지. 중단 기준 필수 | 금지. 불가피하면 PM이 사유·시각·중단 기준을 시험 이슈에 적고 승인. 예외: 접수 시작 직후 실제 제출 1건(`process/recruiting-season.md` UX-08)은 P3 게이트에서 시즌 이슈에 승인과 공지를 미리 마침. 이 승인은 제출 1건과 그 시험 데이터 삭제에만 적용 |
| C 금지 | 접수 시작일·마감일·합격 발표일의 부하 테스트, 보호 리소스(RDS, S3, CloudFront) 변경을 수반하는 시험, 장애·릴리스·시즌 전환 진행 중의 시험 | 하지 않음 | 금지 |

- 등급이 불명확하면 한 단계 높게 분류
- 배포를 수반하는 시험은 배포 금지 기간 규칙(`process/release.md` "배포 금지")을 따름

### 공지

| 항목 | 규칙 |
|---|---|
| 시점 | A: 시작 30분 전까지. B: 시작 24시간 전까지, 시작 직전에 한 번 더 (초기 기준) |
| 채널 | 경보를 받는 팀 메신저 채널. 공지 글은 고정하고 시험 이슈 링크를 넣음 |
| 작성 | 시험 수행 담당 |
| 필수 내용 | 종류·등급, 시작·종료 예정(절대 날짜·시각), 울릴 수 있는 경보 이름, 대상 Product와 환경, 수행 담당과 확인 담당(서로 다른 사람), 중단 기준 |
| 사용자 공지 | 사용자 영향이 예상되는 B 시험은 PM이 대외 점검 공지 방식(`org/pm-guide.md`)으로 따로 공지 |

### 경보 시험 방법

| 방법 | 규칙 |
|---|---|
| 경보 상태 강제 변경(`set-alarm-state`) | 사용함. 사유 문구 앞에 `[시험]`을 붙임. 경보 설정을 바꾸지 않아 Terraform 코드와 차이(drift)가 생기지 않음 |
| 경보 알림 끄기(`disable-alarm-actions`) | 금지. 실제 장애를 놓치고, 다시 켜지 않으면 알림이 꺼진 채 남음 |
| 임계값 임시 변경 | 금지. 기존 경보 조건 변경은 장애 대응일 때만 허용(product-infra 결정 기록 "시즌 중 콘솔 변경 범위") |

- 경보(ALARM) 판정: 공지 범위 안에서 상태 강제 변경으로 울린 `[시험]` 표시 ALARM만 시험으로 봄. 공지 목록에 있는 경보라도 지표가 실제로 넘어서 울린 ALARM(사유에 `[시험]` 없음)은 실제 장애로 봄
- 정상(OK) 복구 판정: 복구 알림에는 사유가 표시되지 않음. 수행 담당이 해당 경보의 상태 전환 기록(경보 기록 탭)에서 직전 ALARM이 `[시험]` 강제 변경이었는지 확인하고 공지 글에 적음. 확인 전에는 실제 장애의 복구일 수 있다고 봄
- 부하 테스트 중에도 경보는 켜 둠. 울릴 수 있는 경보는 공지에 미리 적음

### 실행과 종료

| 단계 | 작업 | 완료 조건 |
|---|---|---|
| 준비 | 시험별 성공 조건을 시험 이슈에 적음(경보 도착 시험: 알림 도착 시간. DB 복원 시험: `process/recruiting-season.md` INF-05의 복원 시간·행 수 대조·시험 DB 삭제. 제출 시험: UX-08 기준). B 시험은 확인 담당이 참석을 회신하고, 수행 담당 없이도 시험을 멈출 수단(부하 도구 정지 권한 등)을 확인함 | 성공 조건 기록, 확인 담당 회신 |
| 시작 | 진행 중인 장애·배포·시즌 전환이 없는지 확인. 부하 도구는 자동 종료 시각을 설정함. 시작 공지 | 공지 글에 시작 시각 기록 |
| 수행 | 공지한 범위 안에서만 수행 | 준비 단계의 성공 조건 확인 |
| 종료 | 바꾼 상태·시험 데이터를 원상 복구. 종료 공지 | 시험 경보 전부 OK, 경보 알림 켜짐 |
| 확인 | 확인 담당이 OK 상태와 원상 복구를 직접 확인 | 공지 글에 확인 답글 |

- 종료 예정 시각을 넘기면 중단하고 사유를 공지함

### 시험 중 실제 장애가 겹칠 때

| 상황 | 조치 |
|---|---|
| 공지 목록에 없는 경보, `[시험]` 표시가 없는 ALARM | 실제 장애로 보고 시험 중단. "단계"의 접수로 전환 |
| 시험 경보가 예정 횟수·시간을 넘어 계속 옴, 사용자 제보 도착, 중단 기준 초과 | 시험 즉시 중단. 시험이 원인인지는 중단 뒤 판별 |
| 수행 담당과 연락이 안 됨 | 시험 중단으로 보고 확인 담당이 준비 단계에서 확인한 수단으로 직접 멈춤 |

- 중단은 팀원 누구나 요청할 수 있음. 공지 글에 "중단"으로 답하고 이유는 나중에 확인
- 중단 완료는 시험 요청이 멈춘 것을 지표로 확인한 때로 기록함
- 재개는 PM 승인. 장애 대응이 끝난 뒤에만 함
- 시험 때문에 생긴 사용자 영향은 장애로 취급해 이 문서의 심각도·공지·사후 분석 기준을 적용

### 부하 테스트 추가 조건

| 항목 | 조건 |
|---|---|
| 목적·규모 | 목표 요청 수, 지속 시간, 대상 API를 시험 이슈에 정함 |
| 합산 상한 | 모든 부하 발생기를 합친 초당 요청 수와 동시 요청 수의 상한을 정함. 낮은 부하에서 시작해 단계적으로 올리고, 단계마다 사용자 지연·오류율·DB 여유를 확인. 상한을 도구에서 강제할 수 없으면 시험하지 않음 |
| 시험 전 확인 | 서버 CPU 크레딧, DB CPU 크레딧·여유 메모리·연결 수 |
| 요청 제한(WAF) | 시험 IP 허용 규칙을 넣지 않음(콘솔 변경이라 코드와 차이가 생김). IP당 제한 미만으로 나누거나 제한이 걸린 경로를 시험 범위에서 뺌 |
| 캐시 | CDN 캐시에서 나간 응답은 서버 부하가 아님. 캐시를 거치지 않는 경로로 시험 |
| 시험 데이터 | 쓰기 시험은 식별 접두어와 삭제 방법을 미리 정함. 운영 DB 삭제는 PM 승인 뒤 실행 |
| 시간대 | 사용량이 가장 적은 시간대 |
| AWS 신고 | 부하 테스트 사전 신고 필요 여부를 AWS 공식 정책으로 확인해 시험 이슈에 기록 |

|---|---|

| 결과, 알림 도착 시간, 중단 여부, 원상 복구 확인 | 같은 이슈 댓글 |

| 기록 대상 | 장애 대응 중 수행한 설정 변경, 되돌리기, 복원 |
| 기록 위치 | 해당 이슈의 댓글 |
| 기록 항목 | 변경 일시(절대 날짜), 변경 내용 요약, 수행 역할, 결과 |
| 식별자 | 자원 ID, 계정 ID, 주소는 공개 이슈에 적지 않음. 비공개 운영 문서에 기록 |

## 회고 기록 원칙

- 사람이 아닌 절차와 구조를 대상으로 작성. 책임 소재 서술 금지
- 사실과 대응만 기재. 시각은 절대 날짜로 기록
- 공개 문서에는 일반화해서 작성. 자원 ID, 호스트명, 내부 링크, 개인 정보 제외
- 상세 기록은 비공개 위치에 보관
- 재발 방지 액션은 담당 역할, 기한(절대 날짜), 완료 조건을 가진 이슈로 등록
- 규칙 자체를 바꾸는 경우 결정 기록 작성(`decisions/`)

## 사후 분석 작성 조건과 양식

다음 중 하나에 해당하면 사후 분석(postmortem)을 작성함

| 조건 |
|---|
| 사용자가 체감한 장애 |
| 데이터 유실 위험이 있었던 장애 |
| 되돌리기를 수행한 경우 |
| 경보가 아니라 사람이 먼저 발견한 경우 |

| 양식 항목 | 내용 |
|---|---|
| 요약 | 무슨 일이 있었는지 2~3줄 |
| 영향 범위·시간 | 영향받은 기능·사용자 범위, 시작·종료 시각(절대 날짜) |
| 타임라인 | 발생, 접수, 완화, 복구 시각과 수행한 작업 |
| 원인 | 직접 원인과 그것을 막지 못한 절차·구조 |
| 잘한 점 | 효과가 있었던 대응 |
| 개선할 점 | 늦었거나 부족했던 부분 |
| 후속 작업과 담당 역할 | 이슈로 등록. 담당 역할, 기한, 완료 조건 |

- 작성 원칙은 위 "회고 기록 원칙"을 따름
