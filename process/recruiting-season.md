# 모집 시즌 체크리스트

매 기수 서류 모집을 준비하고 끝내는 데 필요한 공통 기술 확인 항목. 세로 A4 인쇄를 고려해 표 열을 5개로 고정하고 문장을 짧게 씀. 기수 한정 작업(특정 PR, 배포 예정일)은 이 문서에 쓰지 않고 시즌 이슈에 씀

## 1. 이 문서의 범위와 다른 문서와의 관계

| 대상 | 이 문서가 다루는 것 | 규칙 본문이 있는 곳 |
|---|---|---|
| 동결과 배포 금지 | 금지 구간을 정했는지, 막는 방법이 동작하는지 확인 | `process/release.md`(연간 운영 일정, 모집 시즌 전환과 겹칠 때). 이 문서는 규칙을 다시 쓰지 않고 가리키기만 함 |
| 장애와 마감 연장 | 장애 대응 1쪽과 호출 연습 확인 | `process/incident.md`(마감 연장은 대표진 결정) |
| 인프라 절차 | 인프라 항목의 통과 기준과 증빙 | product-infra 시즌 런북(`docs/guides/season-runbook.md`). 명령, 자원 이름, ID는 거기와 비공개 기록에만 둠 |
| 인프라 증빙 | 시즌 준비 상태 기록 | product-infra 시즌 기록(`docs/records/`). 예: `docs/records/2026-12-season-readiness.md` |
| 시즌 진행 | 단계 게이트와 항목 상태 | 시즌마다 만드는 engineering-playbook 이슈(시즌 이슈) |

- 이 문서는 "무엇을 어떤 기준으로 확인하는가"만 정함. 어떻게 실행하는가는 위 문서를 따름
- 서류 모집 시작일을 D-day로 씀. D-30은 시작 30일 전, D-1은 시작 전날
- 마감 뒤 단계(P6 이후)는 D-N이 아니라 단계 이름으로 부름
- 날짜는 이 문서에서 상대 기한으로 씀. 시즌 이슈와 기록에는 절대 날짜(`2026-11-24` 형식)를 씀
- 이 문서는 계획한 구조가 모두 구현된 상태를 기준으로 함. 기준 상태는 아래와 같음
  - 시즌 전환은 product-infra의 시즌 변수(용량, API 원본)를 바꾸는 PR과 apply로 함. 시즌 전용 경보도 같은 코드로 생성·삭제됨
  - 운영 DB 스키마는 마이그레이션 도구로 변경하고 적용 이력이 남음
  - 서류 평가와 최종 평가는 관리자 콘솔에서 함
  - 지원서 제출 시 동의 항목, 시각, 문구 버전이 서버에 저장됨
- 기준 상태가 아직 구현되지 않아 확인할 수 없는 항목은 "통과"로 적지 않음. 시즌 기록에 "실패" 또는 "예외 승인"으로 적고, 임시 대응(수동 절차 등)과 구현 이슈 번호를 함께 적음

## 2. 사용법

### 시즌 이슈 여는 법(D-30)

1. 서류 모집 시작 30일 전까지 PM이 대표진에게 그 기수의 모집 일정(서류 모집 시작·마감, 서류 평가, 면접, 합격 발표)을 문의해 받음. 이 문서에는 기수별 날짜를 적지 않음(`process/release.md` "연간 운영 일정")
2. 일정을 받으면 engineering-playbook에 이슈 1건을 만듦. 제목은 `[Docs] 모집 시즌 체크리스트` 뒤에 기수를 붙임
3. 이슈 템플릿의 "작업 상세 내용(check-list)"에 P0~P10 게이트를 체크박스로 적음. 한 줄에 한 단계
4. "작업 내용"에 D-day의 절대 날짜, 서류 모집 마감일, 배포 금지 기간의 시작·끝 날짜(`process/release.md` 규칙으로 계산), 시즌 판단자 역할을 적음
5. 아래 "역할표"의 역할마다 담당을 정함. 이슈에는 이름이 아니라 역할로 적음(사람과 역할의 연결은 팀 Notion)
6. 결정이 필요한 항목은 이 시점에 이슈 댓글로 등록함

### 기록 남기는 법

- 단계가 끝날 때마다 이슈에 댓글 1개를 남김. 항목마다 한 줄씩 아래 4가지를 적음

| 칸 | 내용 |
|---|---|
| 상태 | 대기 / 통과 / 실패 / 해당 없음 / 예외 승인 |
| 날짜 | 확인한 절대 날짜 |
| 확인자 | 확인한 역할 |
| 증빙 | 결과 요약, 이슈·PR 번호, 기록 문서 경로 |

- 해당 없음은 사유를 한 줄 적음
- 예외 승인은 시즌 판단자만 함. 사유와 만료 시점을 적음
- 자원 ID, 계정 ID, 주소, 개인정보가 든 증빙은 이슈에 쓰지 않음. 인프라는 product-infra 시즌 기록에 쓰고 이슈에는 그 경로만 적음
- 개인정보 파기 증빙 같은 비공개 기록의 보관 위치는 미결(아래 "8. 미결 사항")

### 필수 항목이 실패하면

- 이 문서의 모든 항목은 필수
- 필수 항목이 "실패"이거나 "대기"이면 다음 단계로 넘어가지 않고 보류함
- 시즌 판단자가 "보류 후 진행"과 "중단" 중 하나를 정하고 이슈에 사유를 기록함
- "보류 후 진행"은 항목을 "예외 승인"으로 바꾸고, 실패 원인을 고칠 이슈를 따로 등록함
- 검증하지 못한 항목은 "통과"로 적지 않고 "대기"로 둠

## 3. 역할표

| 역할 | 맡는 일 | 정하는 방법 |
|---|---|---|
| 시즌 판단자 | 게이트 통과·보류·중단, 배포 금지 해제, 원복, 예외 승인을 결정함. 마감 연장은 기준 충족 시 대표진에게 요청하고 수행을 확인함(결정은 대표진) | PM이 맡음. 시즌 이슈에 한 명으로 적고 대리인 1명을 정함 |
| 개인정보 담당 | 동의 기록 확인, 보유·파기 계획, 파기 실행 확인 | Product Engineer 1명을 지정 |
| 인프라 담당 | 인프라와 Terraform 항목 | Product Engineer. 영역을 고정하지 않고 시즌마다 지정 |
| 백엔드 담당 | 지원·평가 API와 데이터 항목 | Product Engineer. 시즌마다 지정 |
| 프론트 담당 | 웹사이트 화면 항목 | Product Engineer. 시즌마다 지정 |
| 관리자 콘솔 담당 | 평가·관리자 화면 항목 | Product Engineer. 시즌마다 지정 |
| 저장소별 담당 | 해당 저장소의 릴리스 항목 | 저장소를 맡은 Product Engineer |
| PM | 일정·다운타임 승인, 대표진 소통 | `org/roles-and-authority.md` |
| 운영진 | 공고·문항 내용 확인, 평가, 통지 | BOAZ 운영진. 팀 Notion에서 관리 |

- P0 끝 조건: 위 역할의 담당이 "미정"인 항목이 0
- 한 사람이 여러 역할을 겸할 수 있음. 겸임하면 시즌 이슈에 기록함
- 역할 정의와 권한은 `org/roles-and-authority.md`가 기준

## 6. 작성 규칙(항목 추가 기준)

항목을 추가하려면 아래를 모두 충족해야 함

| 기준 | 내용 |
|---|---|
| 확인 방법 | 누가 해도 같은 결과가 나오는 방법이 있음 |
| 통과 기준 | 예/아니오나 수치로 판정함. "충분히", "잘" 같은 표현 금지 |
| 한 항목에 확인 하나 | 확인이 둘이면 항목을 나눔 |
| 고칠 일 | 항목이 아니라 이슈로 분리함. 항목은 확인만 함 |
| 담당 | 역할로 적음 |
| 공통성 | 기수 한정 조치(특정 PR, 배포 예정일)는 넣지 않음. 시즌 이슈에 씀. 기한은 상대 기한(D-N) |
| 공개 저장소 | 명령, 자원 이름·ID, IP, 시크릿, 내부 링크를 쓰지 않음(`conventions/doc-writing.md`) |
| ID | 영역 접두사와 번호. 기존 ID를 바꾸거나 재사용하지 않음 |

- 인프라 절차 상세가 필요하면 이 문서에 쓰지 않고 product-infra 시즌 런북에 추가한 뒤 경로만 가리킴
- 동결 규칙 같은 정책은 `process/release.md`에만 둠

## 7. 회고와 개정 절차

시즌마다 P10에서 한 번 회고함

### 승격·삭제·유지 기준

| 대상 | 처리 |
|---|---|
| 실패한 항목의 재발 방지 확인, 시즌 이슈에서 따로 추가한 항목, 해당 없음 사유가 시즌 한정인 항목 | 반복할 가치가 있으면 공통 항목으로 승격 |
| 두 시즌 연속 "해당 없음"인 항목. 원인이 제거된 항목 | 삭제(번호는 비워 둠) |
| 위에 해당하지 않는 시즌 한정 내용 | 시즌 기록에만 유지 |

- 개정은 PR 1건으로 올림. 항목 추가·삭제·통과 기준 수치 변경이 대상
- 단계, 역할, 게이트 규칙을 바꾸면 결정 기록(`decisions/`)을 함께 추가함
- 추정 수치는 이번 시즌 실측값으로 교체함

### 자동화 대상 기준

아래를 모두 충족하는 항목만 자동화를 검토함

| 조건 |
|---|
| 읽기 전용 조회로 확인 가능 |
| 통과 기준이 수치나 상태값 |
| 두 시즌 이상 반복됨 |
| 사람의 판단이 필요 없음 |

- 화면 확인, 운영진 결정, 개인정보 조회는 자동화하지 않고 수동으로 둠
