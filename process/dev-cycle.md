# 개발 주기

## 스프린트

| 항목 | 규칙 |
|---|---|
| 주기 | 격주(14일) |
| 계획 회의 | 스프린트 시작 시 PM 주관. Epic을 Ticket으로 나눠 배분 |
| 회의 일정 | 팀 Notion의 스프린트 관리 페이지에 기재. 요일·시간은 변동 가능 |
| 기록 위치 | 팀 Notion(스프린트, Epic, Ticket). 이 저장소에는 기록하지 않음 |
| 종료 | 완료·이월 처리 후 다음 스프린트 계획 |

- 이유: 일정·배정은 PM이 결정하므로(`org/roles-and-authority.md`) 계획 회의에서 한꺼번에 조정함
- 방법: PM이 Epic을 스프린트 안에서 끝낼 수 있는 Ticket으로 나누어 배분하고, 진행 기록은 팀 Notion에만 남김

## 작업 단위와 연결

| 단위 | 의미 | 기록 위치 | 생성 |
|---|---|---|---|
| Epic | 여러 스프린트에 걸치는 목표 | 팀 Notion 로드맵 | PM |
| Ticket | 스프린트 안에서 끝낼 작업 | 팀 Notion | PM 또는 Product Engineer |
| GitHub 이슈 | 개발 작업 1건 | 해당 Product 저장소 | Ticket 담당자 |
| PR | 이슈의 변경 | 해당 Product 저장소 | Ticket 담당자 |

연결 규칙

- Ticket에는 Epic과 스프린트를 반드시 연결. 미연결 Ticket은 Notion에서 추적 불가
- 개발 Ticket은 GitHub 이슈를 만들고 Ticket에 이슈 번호 기재
- 브랜치·커밋·PR에 이슈 번호 포함(`conventions/git.md`)
- 기획·디자인 Ticket은 GitHub 이슈를 만들지 않음. README 등 저장소 문서 작업은 이슈 생성
- 완료 시 Ticket에 이슈·PR 번호 기재. 디자인 Ticket은 Figma 파일 이름을 기재(공개 문서에는 링크를 적지 않으며 Ticket에만 첨부)
- Ticket 내용 작성 시점: 개발은 PR 머지 후, 기획·디자인은 작업 완료 시 Ticket에 수행 내용과 결과를 적음

왜 이렇게 하는지

- Notion의 Ticket과 GitHub의 이슈·PR이 서로 연결되어 있어야 누구든 작업의 기획 배경과 코드 변경을 함께 찾을 수 있음
- Epic·스프린트에 연결되지 않은 Ticket은 Notion에서 추적할 수 없음

구체적으로 어떻게 하는지

- 개발 Ticket마다 GitHub 이슈를 만들고 Ticket에 이슈 번호를 적음
- 브랜치 이름, 커밋 메시지, PR에 같은 이슈 번호를 넣음(`conventions/git.md`)

## 티켓 생성과 배정

| 구분 | 대상 | 생성 | 담당 지정 | 사전 승인 |
|---|---|---|---|---|
| 승인 필요 작업 | 신규 기능, 기술 방식 선택, 일정 변경, 여러 Product 영향 작업 | PM | PM | PM |
| 단순 작업 | 버그 수정, 문구·스타일 수정, 리팩토링, 문서 보완, 반복 운영 | Product Engineer | 생성자 본인 | 불필요. PM에게 공유 |

- 판단이 애매하면 승인 필요 작업으로 처리
- 기능 착수 여부와 우선순위의 최종 결정: PM(`org/roles-and-authority.md`)
- 스프린트 도중에도 단순 작업은 즉시 생성 가능
- 담당 영역은 고정하지 않음. 배정은 PM이 스프린트 계획에서 조정

왜 이렇게 하는지

- 신규 기능, 기술 방식 선택, 일정 변경, 여러 Product 영향 작업은 PM의 결정 사항이므로 사전 승인이 필요함
- 버그 수정 같은 단순 작업까지 승인을 받으면 결정 대기로 작업이 늦어지므로, 생성자 본인이 담당하고 PM에게는 공유만 함

구체적으로 어떻게 하는지

- 작업이 어느 구분인지 애매하면 승인 필요 작업으로 보고 PM에게 Ticket 생성과 승인을 요청함
- 단순 작업은 Product Engineer가 Ticket을 만들고 담당으로 지정한 뒤 PM에게 알림
- 같은 영역이라도 영향에 따라 구분이 달라짐. 예: DB 인덱스 추가, 느린 쿼리 개선처럼 서비스 영향이 없는 DB 작업은 단순 작업. DB 버전 업그레이드처럼 서비스가 멈추는 작업은 승인 필요 작업(`org/pm-guide.md` 판단 사례 1)

Ticket 생성 체크리스트

- [ ] 해당 스프린트 페이지 안에 Ticket 생성
- [ ] Epic 연결
- [ ] 스프린트 연결
- [ ] 담당자 지정
- [ ] (단순 작업) PM에게 알림
- [ ] (개발) GitHub 이슈 생성 후 Ticket에 연결
- [ ] (완료 시) 이슈·PR 번호 기재
- [ ] (디자인) Figma 파일 첨부

| 우선순위 | 중요성 | 시급성 | 처리 |
|---|---|---|---|

- 방법: 작업마다 중요성과 시급성을 각각 높음·중간·낮음으로 보고 표에서 같은 조합의 처리 방식을 찾음. 작업 우선순위의 최종 결정은 PM(`org/roles-and-authority.md`)

## 이슈 TO-DO 관리

| 시점 | 규칙 |
|---|---|
| PR 생성 | 그 PR로 끝난 TO-DO 항목을 연결된 GitHub 이슈에서 체크 |
| PR 템플릿 | 확인 항목에 "이슈 TO-DO를 갱신했음" 포함. 공통 템플릿은 조직 `.github` 저장소에 둘 예정 |
| 리뷰 | 리뷰어가 이슈의 체크 상태와 PR 내용의 일치 여부 확인 |
| 이슈 종료 | 체크되지 않은 항목이 남아 있으면 이슈를 닫지 않음 |
| 하지 않기로 한 항목 | 취소선을 긋고 이유를 한 줄 기재. 또는 새 이슈로 옮기고 그 번호 기재 |
| PR 없는 작업 | 콘솔 변경, 운영 DB 반영, 시즌 전환 같은 실행 작업은 끝낸 당일 체크. 결과를 이슈 댓글로 기록 |

작성 기준

- TO-DO 1항목 = PR 1건으로 확인할 수 있는 크기
- 확인이 불가능한 큰 항목은 쪼갬

이유

- 담당 영역을 고정하지 않는 체계에서는 누구든 작업을 이어받을 수 있어야 함
- 이슈의 체크 상태가 진행 기록 역할

자동 확인

- 이슈 종료 시 미체크 항목이 있으면 경고 댓글을 남기는 검사
- 2026-12 리크루팅 시즌 이후 `.github` 재사용 워크플로로 도입 검토
