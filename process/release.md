# 릴리스

## 릴리스 절차(dev → main)

| 순서 | 작업 | 담당 |
|---|---|---|
| 1 | `dev`에 릴리스할 변경이 모였는지 확인 | PM |
| 2 | `dev` → `main` PR 생성. 포함 이슈, 주요 변경, 검증 결과 기재 | Product Engineer |
| 3 | 리뷰어 승인, 필수 검사 통과 확인 | 리뷰어 |
| 4 | 머지. 이후 저장소별 배포 자동 실행 | Product Engineer |
| 5 | 배포 결과 확인 | Product Engineer |

- 리뷰어 수: `conventions/code-review.md`
- PR 제목 형식: `[Release] 내용`(`conventions/git.md`)
- 릴리스 PR에는 DB 백필 기록(아래 참조)이 있으면 포함
- 배포 방식은 저장소마다 다름. 백엔드는 GitHub Actions 빌드 후 AWS CodeDeploy 배포. 프론트엔드·관리자는 S3와 CloudFront 서비스
- 배포 후 확인 방법과 담당: [확인 필요: 저장소별 배포 후 점검 항목]

## hotfix

| 순서 | 작업 |
|---|---|
| 1 | `main`에서 `hotfix/이슈번호-짧은-설명` 브랜치 생성 |
| 2 | 수정 후 `main` 대상 PR 생성 |
| 3 | 리뷰 승인 후 머지 |
| 4 | 머지 직후 `dev`에 역머지 PR 생성 |
| 5 | 역머지 머지 확인 |

- 역머지가 누락되면 다음 릴리스에서 수정이 사라질 수 있음
- hotfix 기준: 운영 장애, 데이터 손상 위험, 보안 문제. 그 외는 일반 흐름
- hotfix 승인 권한: 리뷰어 1명 승인. 작성자는 승인할 수 없고 승인 없이 머지하지 않음

## DB 스키마 변경(backend)

상세 규칙은 backend 저장소의 `src/main/resources/db/README.md`가 기준. 아래는 요약

| 항목 | 요약 |
|---|---|
| 도구 | Flyway. 파일 위치 `src/main/resources/db/migration/` |
| 엔티티 변경 | 같은 PR에 마이그레이션 파일 포함. `./gradlew test` 통과 |
| 파일 이름 | `V<버전>__<설명>.sql` |
| 실행된 파일 | 한 번이라도 공유 DB(prod, dev)에 실행된 파일은 수정하지 않음. 새 파일로 추가 |
| 버전 순서 | 새 파일 버전은 `dev`의 모든 파일보다 높아야 함. CI가 못 잡으므로 리뷰에서 확인 |
| 롤백 호환 | 직전 버전 앱이 변경된 스키마에서 동작하는지 확인 |
| 백필 | 마이그레이션에 넣지 않음. 리뷰 후 실행하고 SQL, 실행 일시, 영향 행 수를 배포 PR 본문에 기록 |
| 개인정보 | 개인정보가 담긴 SQL·CSV는 저장소에 올리지 않음 |
| 배포 시간 | RDS 유지보수 시간과 자동 백업 시간을 피함. 시간대는 backend `db/README.md` 참조 |
| 실패 시 | 배포가 직전 버전으로 자동 복귀. 다음 배포 전에 실패 기록 복구 필요. 절차는 backend `db/README.md` 참조 |

- 인프라 동결 기간(2027-01)에는 스키마 적용 주를 product-infra 담당에게 미리 공유
- 프로필별 Flyway 동작과 첫 prod 배포 설정은 backend `db/README.md`가 기준

## 백엔드와 프론트엔드 배포 순서

| 상황 | 순서 | 상태 |
|---|---|---|
| 백엔드 API 응답·요청 DTO 변경 | 백엔드 `dev` 머지 → 프론트엔드 타입 재생성 → 프론트엔드 PR | 확정 |
| 호환되는 추가 변경(필드 추가) | 백엔드 먼저 배포, 그다음 프론트엔드 배포 | 확정 |
| 호환되지 않는 변경(필드 삭제·이름 변경) | 3단계로 나눔: 백엔드에 새 필드 추가 배포 → 프론트엔드가 새 필드로 전환해 배포 → 백엔드에서 옛 필드 삭제 배포. 한 번의 배포로 바꾸지 않음 | 확정 |

- 프론트엔드(`frontend`)의 응답 타입은 백엔드 OpenAPI 스펙에서 생성. DTO 변경 시 `pnpm generate:types` 재실행 필요
- 타입 재생성 알림: 백엔드 DTO를 바꾸는 PR 작성자가 PR 본문에 "프론트엔드 타입 재생성 필요"를 기재하고 팀 Notion의 해당 Ticket에 알림
- 알림 방식 자동화: [확인 필요: 자동 알림 도입 여부]
- `frontend_admin`은 2026-10-31 기준 백엔드 미연동. 연동 시 같은 절차 적용 [확인 필요: 관리자 페이지 타입 생성 방식]

## 모집 시즌 전환과 겹칠 때

| 원칙 | 내용 | 상태 |
|---|---|---|
| 우선순위 | 시즌 전환 작업이 릴리스보다 우선. 전환 전날부터 전환 결과 확인이 끝날 때까지 릴리스 금지, hotfix만 허용 | 확정 |
| DB 스키마 변경 | DB 스키마 변경이 든 릴리스는 시즌 전환과 같은 주에 하지 않음 | 확정 |
| 사전 공유 | 시즌 전환 예정일과 겹치는 릴리스는 PM이 일정 조정 | 확정 |
| 규칙 변경 보류 | 2026-12 리크루팅 시즌 중에는 저장소별 규칙 전환 보류 | 확정 |

- 시즌 전환 현황: 단일 EC2 구성과 ALB + EC2 2대 + RDS Multi-AZ 구성 사이의 전환. backend 저장소의 `infra/scripts/season-up.sh`, `season-down.sh`로 수행 중
- product-infra가 이 전환을 Terraform 변수로 이전 중. 이전 완료 후 절차를 이 문서에 갱신
- 시즌 전환은 PR 없는 실행 작업. 끝낸 당일 이슈 TO-DO 체크와 결과 댓글 필요(`process/dev-cycle.md`)
