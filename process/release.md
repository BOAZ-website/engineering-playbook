# 릴리스

## 릴리스 절차(dev → main)

| 순서 | 작업 | 담당 |
|---|---|---|
| 1 | `dev`에 릴리스할 변경이 모였는지 확인 | PM |
| 2 | `dev` → `main` PR 생성. 포함 이슈, 주요 변경, 검증 결과 기재 | Product Engineer |
| 3 | 리뷰어 승인, 필수 검사 통과 확인 | 리뷰어 |
| 4 | 머지. 이후 저장소별 배포 자동 실행 | Product Engineer |
| 5 | 배포 결과 확인 | Product Engineer |

- 리뷰어 수: `conventions/code-review.md`
- PR 제목 형식: `[Release] 내용`(`conventions/git.md`)
- 릴리스 PR에는 DB 백필 기록(아래 참조)이 있으면 포함
- 배포 방식은 저장소마다 다름. 백엔드는 GitHub Actions 빌드 후 AWS CodeDeploy 배포. 프론트엔드·관리자는 S3와 CloudFront 서비스
- 배포 후 점검: 저장소별 고정 체크리스트를 따름. 점검 담당은 PR을 올린 Product Engineer(5단계)

| 저장소 | 배포 후 점검 항목 |
|---|---|
| backend | 상태 점검(health) 응답, 로그인, 주요 조회 1건 |
| frontend(웹사이트) | 메인 페이지와 모집 페이지 열림, 브라우저 콘솔 오류 없음 |
| frontend_admin | 배포 워크플로 도입 시 정함 |
| product-infra | apply 후 plan이 변경 없음(No changes) |

왜 이렇게 하는지

- `main`에는 `dev`의 검토를 거친 변경만 들어가야 하므로 릴리스는 `dev` → `main` PR 한 경로로만 함(`conventions/git.md`)
- PR에 포함 이슈와 검증 결과를 적어 두면 리뷰어가 무엇이 운영에 나가는지 확인할 수 있음

구체적으로 어떻게 하는지

- PM이 릴리스할 변경이 `dev`에 모였다고 판단하면 Product Engineer가 PR 제목을 `[Release] 내용`으로 올림
- 머지 후 배포 결과를 확인하는 것까지 PR을 올린 Product Engineer가 맡음

## hotfix

| 순서 | 작업 |
|---|---|
| 1 | `main`에서 `hotfix/이슈번호-짧은-설명` 브랜치 생성 |
| 2 | 수정 후 `main` 대상 PR 생성 |
| 3 | 리뷰 승인 후 머지 |
| 4 | 머지 직후 `dev`에 역머지 PR 생성 |
| 5 | 역머지 머지 확인 |

- 역머지가 누락되면 다음 릴리스에서 수정이 사라질 수 있음
- hotfix 기준: 운영 장애, 데이터 손상 위험, 보안 문제. 그 외는 일반 흐름
- hotfix 승인 권한: 리뷰어 1명 승인. 작성자는 승인할 수 없고 승인 없이 머지하지 않음
- hotfix도 머지 후 아래 "운영 배포 승인"을 거쳐야 운영에 반영됨

왜 이렇게 하는지

- 운영에 나간 코드(`main`)에서 바로 분기해야 아직 릴리스되지 않은 `dev`의 변경이 섞이지 않음
- 역머지를 하지 않으면 `dev`에 수정이 없어서 다음 릴리스에서 수정이 사라질 수 있음

구체적으로 어떻게 하는지

- `main`에서 `hotfix/이슈번호-짧은-설명` 브랜치를 만들어 `main` 대상 PR을 올리고, 머지 직후 같은 브랜치로 `dev` 대상 PR을 하나 더 올림
- hotfix PR의 첫 응답은 당일(`conventions/code-review.md`)

## 운영 배포 승인

`main`에 머지하면 배포 워크플로가 자동으로 시작되지만, 운영 배포 job은 승인 전까지 대기(Waiting) 상태로 멈춤. GitHub 저장소 설정의 배포 환경(environment) `production`에 걸린 승인 규칙 때문이며, 승인자 1명이 승인해야 운영에 반영됨

### 규칙

| 항목 | 규칙 |
|---|---|
| 대상 | `main` 머지 후 실행되는 운영 배포 job. job에 `environment: production` 지정 |
| 승인자 | 26&27기까지는 `2nd-PMO` 팀. 27&28기부터는 그 기수의 PM 팀 + 해당 Product 담당자 1명. 승인자 중 1명이 승인하면 진행 |
| 본인 승인 금지 | 배포를 시작한 사람(`main`에 머지한 사람)은 승인할 수 없음. GitHub 설정은 PR 작성자를 막지 않음 |
| 작성자 승인 금지 | PR 작성자도 그 배포를 승인하지 않음. GitHub가 자동으로 막지 않으므로 승인자가 직접 확인 |
| 머지 | PR 작성자가 리뷰 승인 후 머지. 그러면 본인 승인 금지가 작성자를 막고 승인은 다른 쪽이 함 |
| 관리자 우회 | 26&27기: 금지. 저장소 관리자도 승인 없이 진행할 수 없음. 27&28기부터: 긴급 배포에만 허용(아래 "긴급 배포") |
| 배포 브랜치 | `main`만 허용 |
| 승인 대기 상한 | 30일(GitHub 제한) |

- 27&28기부터: 담당자가 작성한 PR은 담당자가 머지하고 PM 팀이 승인함. PM이 작성한 PR은 PM이 머지하고 담당자가 승인함. 그래서 승인자를 이 두 쪽으로 둠
- 26&27기: 작성자가 머지하고 `2nd-PMO` 팀의 다른 팀원이 승인함. 작성자·머지한 사람 제외 승인자가 있도록 팀원은 2명 이상 유지
- 작성자가 머지할 수 없는 경우(부재 등): 작성자·머지한 사람이 아닌 승인자 중 승인 가능한 사람이 승인함. 없으면 배포를 대기시킴
- 긴급 배포: 심각도 "높음" 장애(`process/incident.md`)를 고치는 hotfix 배포
  - 26&27기: 우회 없음. 머지한 사람이 팀 메신저에서 `2nd-PMO` 팀원 전원을 바로 호출하고, 승인자는 30분 안(모집 기간 15분 안)에 응답함. 승인자가 3명이라 대개 1명은 응답할 수 있음
  - 27&28기부터: 승인자(PM 팀 + 담당자)가 2명뿐이라 작성자를 빼면 1명만 남음. 그 1명이 30분 안(모집 기간 15분 안)에 응답하지 않으면 저장소 관리자가 승인 없이 배포할 수 있음(관리자 우회)
  - 관리자 우회를 쓰면 24시간 안에 사후 기록을 남김: hotfix PR에 우회 사유, 호출 시각, 응답이 없던 승인자 역할을 댓글로 적고, 장애 이슈에도 같은 내용을 적음. 다음 주간 회의에서 PM 팀이 사후 확인함
  - 관리자 우회는 긴급 배포에만 씀. 일반 배포에서 우회한 기록이 나오면 PM이 경위를 확인하고 재발 방지책을 정함
- 롤백 방법 기재: DB 스키마 변경과 인프라 변경 PR만 승인 요청에 필수. 일반 배포는 되돌리기(revert) PR로 충분
- AWS 배포 롤은 `production` 환경에서 실행된 job만 받아들임. 승인 단계를 건너뛰는 다른 배포 경로를 만들지 않음

왜 이렇게 하는지

- 머지한 사람이 혼자 운영에 반영하지 못하게 해서, 리뷰와는 별도로 운영 반영 직전에 한 번 더 확인함
- 작성자가 머지하고 다른 쪽이 승인하는 구조라서, 작성자가 자기 변경을 승인하는 일이 없음

구체적으로 어떻게 하는지

- 머지한 사람이 Actions에서 대기 상태를 확인하고 팀 메신저로 승인을 요청하면, 승인자가 아래 "승인 전 확인"을 거쳐 승인 또는 Reject함

| 28&29기 | `4th-PM` 팀 + Product 담당자 1명 |
| 29&30기 | `5th-PM` 팀 + Product 담당자 1명 |

- PM 팀 번호 계산식(27&28기부터): 번호 = 앞 기수 번호 − 24. 예: 35&36기는 `11th-PM`

### 승인 절차

| 순서 | 작업 | 담당 |
|---|---|---|
| 1 | `main` 머지 후 Actions에서 배포 실행이 대기(Waiting) 상태인지 확인 | 머지한 사람 |
| 2 | 팀 메신저로 승인 요청. 실행 링크와 머지한 PR 번호 기재 | 머지한 사람 |
| 3 | 아래 "승인 전 확인" 수행 | 승인자 |
| 4 | 실행 페이지에서 Review deployments 선택 → 환경 선택 → 필요하면 코멘트 → Approve and deploy | 승인자 |
| 5 | 배포 job 성공과 서비스 동작 확인 | 머지한 사람 |

### 승인 전 확인

| 항목 | 확인 내용 |
|---|---|
| 빌드 | 배포 앞 단계 job(빌드, 검사)이 모두 성공 |
| 대상 커밋 | 실행이 머지한 PR의 커밋에서 시작됨 |
| 작성자·머지한 사람 | 승인자가 PR 작성자나 머지한 사람이 아님. 해당하면 승인하지 않고 다른 승인자에게 넘김 |
| 더 최신 배포 | 이 실행보다 나중에 시작된 같은 저장소의 운영 배포가 이미 성공했으면 승인하지 않음. 이 실행은 Reject하고, 필요하면 최신 `main`에서 다시 배포 |
| 시기 | 모집 시즌 전환 금지 기간이 아님. 금지 기간에는 hotfix만 승인 |
| DB 스키마 변경 | 포함 시 RDS 유지보수·백업 시간대를 피함(위 "DB 스키마 변경") |
| 인프라 | product-infra는 plan 결과에 보호 자원 삭제·교체(`delete`/`replace`)가 없음. 있으면 `products/infra.md` 절차를 따름 |
| 롤백 방법 | DB 스키마 변경 PR과 인프라 변경 PR은 승인 요청에 롤백 방법이 적혀 있어야 함. 없으면 승인하지 않음 |

- 하나라도 충족하지 않으면 Reject를 누르고 코멘트에 사유를 적음. Reject하면 워크플로가 실패 처리됨
- 문제를 고친 뒤 다시 머지하거나 실행을 다시 시작하면 다시 승인을 받아야 함
- 더 최신 배포 확인 방법: 저장소 Actions에서 같은 배포 워크플로의 실행 목록을 보고, 승인하려는 실행보다 나중에 시작해 성공한 운영 배포가 있는지 봄. 이유는 오래 대기한 릴리스를 뒤늦게 승인하면 그 사이 먼저 배포된 hotfix 수정이 운영에서 사라질 수 있기 때문
- 승인 대기 실행이 2개 이상이면 가장 최신 실행만 승인하고 나머지는 Reject함. 승인 전에 최신 실행이 이전 변경을 모두 포함하는지(같은 `main` 이력인지) 확인
- 운영을 이전 버전으로 되돌리는 일은 이 절차가 아니라 Product별 "배포와 되돌리기" 절차로 하고 장애·변경 기록에 남김

## DB 스키마 변경(backend)

상세 규칙은 backend 저장소의 `src/main/resources/db/README.md`가 기준. 아래는 요약

| 항목 | 요약 |
|---|---|
| 도구 | Flyway. 파일 위치 `src/main/resources/db/migration/` |
| 엔티티 변경 | 같은 PR에 마이그레이션 파일 포함. `./gradlew test` 통과 |
| 파일 이름 | `V<버전>__<설명>.sql` |
| 실행된 파일 | 한 번이라도 공유 DB(prod, dev)에 실행된 파일은 수정하지 않음. 새 파일로 추가 |
| 버전 순서 | 새 파일 버전은 `dev`의 모든 파일보다 높아야 함. CI가 못 잡으므로 리뷰에서 확인 |
| 롤백 호환 | 직전 버전 앱이 변경된 스키마에서 동작하는지 확인 |
| 백필 | 마이그레이션에 넣지 않음. 리뷰 후 실행하고 SQL, 실행 일시, 영향 행 수를 배포 PR 본문에 기록 |
| 개인정보 | 개인정보가 담긴 SQL·CSV는 저장소에 올리지 않음 |
| 배포 시간 | RDS 유지보수 시간과 자동 백업 시간을 피함. 시간대는 backend `db/README.md` 참조 |
| 실패 시 | 배포가 직전 버전으로 자동 복귀. 다음 배포 전에 실패 기록 복구 필요. 절차는 backend `db/README.md` 참조 |

- 인프라 동결 기간(모집 시즌 전환 전후)에는 스키마 적용 주를 product-infra 담당에게 미리 공유
- 프로필별 Flyway 동작과 첫 prod 배포 설정은 backend `db/README.md`가 기준

왜 이렇게 하는지

- 이미 실행된 마이그레이션 파일을 고치면 공유 DB와 파일 내용이 어긋나므로 새 파일로 추가함
- 배포가 실패하면 직전 버전으로 복귀하므로, 직전 버전 앱이 바뀐 스키마에서도 동작해야 함

구체적으로 어떻게 하는지

- 엔티티를 바꾸는 PR에 마이그레이션 파일을 함께 넣고, 리뷰어는 새 파일의 버전이 `dev`의 모든 파일보다 높은지 확인함(CI가 잡지 못함)
- 백필은 마이그레이션에 넣지 않고, 리뷰 후 실행한 뒤 SQL, 실행 일시, 영향 행 수를 배포 PR 본문에 적음

## 백엔드와 프론트엔드 배포 순서

| 상황 | 순서 | 상태 |
|---|---|---|
| 백엔드 API 응답·요청 DTO 변경 | 백엔드 `dev` 머지 → 프론트엔드 타입 재생성 → 프론트엔드 PR | 확정 |
| 호환되는 추가 변경(필드 추가) | 백엔드 먼저 배포, 그다음 프론트엔드 배포 | 확정 |
| 호환되지 않는 변경(필드 삭제·이름 변경) | 3단계로 나눔: 백엔드에 새 필드 추가 배포 → 프론트엔드가 새 필드로 전환해 배포 → 백엔드에서 옛 필드 삭제 배포. 한 번의 배포로 바꾸지 않음 | 확정 |

- 프론트엔드(`frontend`)의 응답 타입은 백엔드 OpenAPI 스펙에서 생성. DTO 변경 시 `pnpm generate:types` 재실행 필요
- 타입 재생성 알림: 백엔드 DTO를 바꾸는 PR 작성자가 PR 본문에 "프론트엔드 타입 재생성 필요"를 기재하고 팀 Notion의 해당 Ticket에 알림
- 알림 방식 자동화: 도입하지 않음. PR 작성자가 PR 본문 기재로 직접 알림. 놓치는 일이 반복되면 CI의 OpenAPI 차이 검출 도입을 검토
- `frontend_admin`은 2026-10-31 기준 백엔드 미연동. 연동 시 같은 절차 적용 [확인 필요: 관리자 페이지 타입 생성 방식]

## 연간 운영 일정

BOAZ 전체 일정 중 서비스 운영에 영향을 주는 시기. 상반기 기준이며 괄호는 하반기. 대략적인 시기이고 기수마다 바뀌므로, 매 기수 운영진 공지로 실제 날짜를 확인함

| 시기 | BOAZ 일정 | 서비스운영팀 작업 |
|---|---|---|
| 11월 넷째 주~12월 셋째 주(5~6월) | 차기 기수 서류 모집 | 모집 시작 전 season-up과 모집 정보 반영 완료. 모집 기간에는 릴리스 금지, hotfix만 허용. 서류 모집 마감 직후 season-down |
| 12월~1월 둘째 주(6~7월) | 기말고사 휴식 | 큰 인프라 작업을 피함 |
| 1월 첫째 주(7월) | 신입 기수 면접 | 시즌 구성 없이 운영. 모집 관리 기능 안정 운영 |
| 1월 둘째 주(7월) | 신입 기수 OT | 이 주와 컨퍼런스 사이가 서비스운영팀 기수 교체일. 교체일 전 2주가 인계 기간(`org/handover.md`) |
| 1월 셋째 주(7월), 3월 첫째 주(9월) | 방학·학기 세션 시작 | 출결 관리 기능을 세션 시작 전에 준비 |
| 1월 넷째 주 토요일(7월), 5월 첫째·둘째 주 토요일(11월) | 컨퍼런스, 컨퍼런스톡 | 행사 콘텐츠 반영. 행사 직전 배포 자제 |
| 4월 셋째~넷째 주(10월) | 중간고사 휴식 | 큰 작업을 피함 |

- 밀 수 없는 날짜: 서류 모집 시작, 면접, OT, 세션 시작. 이 날짜에 걸린 작업은 범위를 줄여서라도 날짜를 지킴
- 모집 시즌 준비 점검: `process/recruiting-season.md`(서류 모집 시작 30일 전부터 시즌 이슈로 진행)
- 해커톤은 연 1회 원칙이나 기수마다 열리지 않을 수 있음

## 모집 시즌 전환과 겹칠 때

| 원칙 | 내용 | 상태 |
|---|---|---|
| 우선순위 | 시즌 전환 작업이 릴리스보다 우선. 전환 전날부터 전환 결과 확인이 끝날 때까지 릴리스 금지, hotfix만 허용 | 확정 |
| DB 스키마 변경 | DB 스키마 변경이 든 릴리스는 시즌 전환과 같은 주에 하지 않음 | 확정 |
| 사전 공유 | 시즌 전환 예정일과 겹치는 릴리스는 PM이 일정 조정 | 확정 |
| 규칙 변경 보류 | 2026-12 리크루팅 시즌 중에는 저장소별 규칙 전환 보류 | 확정 |

- 시즌 전환 현황: 단일 EC2 구성과 ALB + EC2 2대 + RDS Multi-AZ 구성 사이의 전환. backend 저장소의 `infra/scripts/season-up.sh`, `season-down.sh`로 수행 중
- product-infra가 이 전환을 Terraform 변수로 이전 중. 이전 완료 후 절차를 이 문서에 갱신
- 시즌 전환은 PR 없는 실행 작업. 끝낸 당일 이슈 TO-DO 체크와 결과 댓글 필요(`process/dev-cycle.md`)
- 동결 규칙은 이 절이 기준. 금지 구간을 정했는지와 막는 방법이 동작하는지의 확인 항목은 `process/recruiting-season.md`(REL-01, REL-02)

왜 이렇게 하는지

- 시즌 전환 작업이 릴리스보다 우선하므로 겹치는 기간에는 릴리스를 막음
- 구체적으로: 전환 전날부터 결과 확인이 끝날 때까지 hotfix만 허용하고, 스키마 변경이 든 릴리스는 전환과 같은 주에 하지 않음
