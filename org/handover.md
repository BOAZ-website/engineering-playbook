# 인수인계

서비스운영팀은 약 6개월마다 기수가 바뀜. 이 문서는 기수 교체 체크리스트

## 결정 사항

| 항목 | 규칙 |
|---|---|
| 인수 확인 조건 | 인수받는 사람이 playbook대로 한 번 해 보고 어긋난 부분을 PR로 고침 |
| 권한 이전 | 신규 보유자 확정 후 퇴임자 권한 회수 |
| 총괄 | PM |

- 근거: 규칙이 사람을 따라 사라지는 문제를 막기 위함
- 근거: 직접 실행해야 문서의 빈 곳이 드러남

## 시점

| 시점 | 작업 |
|---|---|
| 기수 교체 4주 전 | 인수인계 이슈 생성. 항목별 담당과 기한 지정 |
| 기수 교체 2주 전 | 권한 이전, 진행 중 작업 정리 |
| 기수 교체일 | 퇴임자 권한 회수 |
| 기수 교체 2주 후 | 인수 확인(playbook 실행 결과 PR 머지) |

- 시즌 전환 기간과 겹치면 PM이 일정 조정(`process/release.md`)
- 기수 교체일: 기수마다 PM이 정해 인수인계 이슈에 적음 [확인 필요: 27&28기 → 28&29기 교체일]

왜 이렇게 하는지

- 권한 이전을 교체일 2주 전에 끝내야 교체일에 퇴임자 권한만 회수하면 됨
- 교체 2주 후에 인수받는 사람이 playbook대로 직접 해 보면 문서의 빈 곳이 드러남

구체적으로 어떻게 하는지

- PM이 교체 4주 전에 인수인계 이슈를 만들고, 이 문서의 항목별로 담당과 기한을 적음
- 시즌 전환 기간과 겹치면 PM이 일정을 조정함

## 진행 중 작업과 미결 결정

| 항목 | 담당 | 완료 조건 |
|---|---|---|
| 열린 이슈·PR 목록 정리. 이어받을 사람 지정 | 퇴임 Product Engineer | 이슈마다 담당 역할 지정 |
| 각 문서의 미결 표 정리 | PM | 미결마다 결정 주체와 시점 갱신 |
| 진행 중 결정의 논의 경위 기록 | 퇴임 Product Engineer | 이슈 또는 결정 기록에 반영 |
| 팀 Notion 티켓 상태 갱신 | PM | 진행 중 티켓의 담당 변경 |

- 이유: 담당 영역을 고정하지 않으므로, 이슈의 담당 역할과 논의 경위가 남아 있어야 새 팀원이 작업을 이어받을 수 있음
- 방법: 퇴임 Product Engineer가 열린 이슈·PR마다 이어받을 사람을 지정하고, 논의 경위를 이슈 또는 결정 기록에 옮김

## 접근 권한 이전과 회수

| 순서 | 작업 | 담당 |
|---|---|---|
| 1 | 신규 보유자 지정, 팀 Notion 보유자 목록 갱신 | PM |
| 2 | 2명 이상 보유 규칙 충족 확인 | PM |
| 3 | 퇴임자의 저장소, AWS, 조직, 경보 수신 그룹, 시크릿 접근 회수 | 해당 권한 보유자 |
| 4 | 회수 완료 기록 | PM |

- 상세: `org/access.md`
- 이유: 회수 전에 후임 보유자가 확정되어 있어야 2명 이상 보유 규칙이 깨지지 않고 권한 행사가 끊기지 않음
- 방법: PM이 신규 보유자를 팀 Notion 목록에 먼저 반영한 뒤, 각 권한 보유자가 퇴임자의 접근을 회수하고 PM이 완료를 기록함

## GitHub 팀 교체

기수마다 GitHub 조직에 기수 팀(팀원 전체)과 PM 팀을 새로 만듦. 팀 이름 규칙: `org/roles-and-authority.md`의 "기수별 GitHub 팀"

| 순서 | 작업 | 담당 |
|---|---|---|
| A | 새 기수 팀 생성, 새 기수 팀원 전체 추가 (기수 시작 전) | GitHub 조직 소유자 |
| B | 아래 "승인 팀 교체" 수행 | 아래 표 참조 |
| C | 이전 기수 팀 정리. 새 기수 팀 확인 후 처리하며, 이전 기수 팀의 저장소 권한 회수 포함 | GitHub 조직 소유자 |

- engineering-playbook 관리 주체는 기수 교체 때 새 기수의 PM 팀으로 넘어감. 관리 주체는 `main` 보호 규칙의 PM 예외 팀과 저장소 maintain 권한을 가진 팀. 이전 PM 팀은 새 팀 확인 후 제거함(아래 4~6단계)

### 승인 팀 교체

기수마다 PM 팀을 새로 만들어 운영 배포 승인자와 playbook PM 예외를 넘김. 26&27기의 `2nd-PMO` 팀에서 27&28기 `3rd-PM` 팀으로 넘기는 교체도 같은 순서를 따름. 팀 이름 규칙: `process/release.md`의 "기수별 승인 팀"

| 순서 | 작업 | 담당 |
|---|---|---|
| 1 | 새 기수 PM 팀(`n`th-PM) 생성, 신임 PM 추가 | GitHub 조직 소유자 |
| 2 | 새 팀에 backend, frontend, frontend_admin, product-infra 읽기 권한 부여 | GitHub 조직 소유자 |
| 3 | 4개 저장소 `production` 환경 승인자에 새 팀 추가, Product 담당 승인자를 새 담당자로 교체 | 저장소 관리자 |
| 4 | engineering-playbook `main` 보호 규칙의 PM 예외 팀을 새 팀으로 교체, 저장소 maintain 권한 부여 | GitHub 조직 소유자 |
| 5 | 다음 운영 배포에서 신임 PM 또는 새 담당자가 승인할 수 있는지 확인 | 신임 PM |
| 6 | 이전 팀(PMO 또는 PM 팀)을 환경 승인자와 playbook 예외에서 제거 | GitHub 조직 소유자 |

- 새 팀을 먼저 추가하고 확인한 뒤 이전 팀을 제거함. 순서를 바꾸면 승인자가 없는 기간이 생김
- 승인자는 저장소 읽기 권한 이상이 있어야 함
- 이유: 이전 팀을 먼저 제거하면 다음 운영 배포를 승인할 사람이 없어 배포가 대기 상태로 멈춤
- 방법: 순서 5에서 신임 PM 또는 새 담당자가 실제 운영 배포를 승인해 본 뒤에 순서 6의 제거를 진행함

## 시크릿과 키 교체 대상

| 종류 | 교체 조건 |
|---|---|
| 퇴임자가 알고 있던 시크릿 | 교체 |
| 개별 발급한 API 접근 키 | 폐기 후 재발급 |
| 서버 환경 변수의 인증 서명 값 | 교체 시 사용자 재로그인 영향 확인 후 결정 |
| 소셜 로그인 앱 자격 값 | 퇴임자가 소유자면 이전 또는 교체 |
| OpenAPI 스펙 접근 인증 값 | 교체 |

- 값과 보관 위치는 이 문서에 적지 않음. 비공개 운영 문서 참조
- 교체 일정과 영향은 PM이 승인
