# 역할과 결정 권한

근거: `decisions/0002-team-structure.md`

## 역할 정의

| 역할 | 인원 | 정의 |
|---|---|---|
| PM | 1명 | 서비스운영팀 팀장. 기술 결정까지 맡는 Technical Product Manager |
| Product Engineer | 3명 | 담당 영역을 고정하지 않고 5개 Product 전체를 다루는 엔지니어 |

- PM은 서비스운영팀장이 맡음. 서비스운영팀장은 이전 기수에서 올라온 사람
- 인원은 다음 기수부터의 체계 기준
- 역할명과 사람의 연결은 팀 Notion에서 관리. 이 저장소에 적지 않음

## 기수별 GitHub 팀

기수는 약 6개월마다 바뀜. 매 기수마다 GitHub 조직(BOAZ-website)에 아래 두 팀을 새로 만듦

| 팀 | 구성 | 이름 규칙 |
|---|---|---|
| 기수 팀 | 그 기수 PM과 Product Engineer 전원 | `n`th-engineer. 번호는 PM 팀과 같음 |
| PM 팀 | 그 기수 PM | `process/release.md`의 "기수별 승인 팀" 참조 |

| 항목 | 규칙 |
|---|---|
| 생성 담당 | GitHub 조직 소유자 |
| 생성 시점 | 기수 시작 전 |
| 이전 기수 팀 정리 | `org/handover.md`의 "GitHub 팀 교체" |

| 기수 | 기수 팀 | PM 팀 |
|---|---|---|
| 26&27기 | 기존 파트별 팀(`2nd-backend`, `2nd-frontend`, `2nd-design`, `2nd-infra`) | `2nd-PMO` |
| 27&28기 | `3rd-engineer` | `3rd-PM` |
| 28&29기 | `4th-engineer` | `4th-PM` |
| 이후 | `5th-engineer`, `6th-engineer`, … 기수마다 번호 1씩 증가 | `5th-PM`, `6th-PM`, … |

- 26&27기까지는 파트별 팀(기수 번호-파트 형식)을 씀. 27&28기부터 파트 구분이 없어지므로(Product Engineer) 기수 팀 하나로 합침
- engineering-playbook 관리 주체는 기수마다 그 기수 PM 팀으로 넘어감. 절차: `org/handover.md`

## 결정 권한 (초안)

팀 합의 전 초안. 합의 후 상태를 "확정"으로 변경하고 결정 기록을 추가

| 결정 사항 | PM | Product Engineer |
|---|---|---|
| 대표진 소통 | 담당 | 해당 없음 |
| 인력 배정 | 결정 | 의견 제시 |
| 일정 조정 | 결정 | 의견 제시 |
| 기능 착수 여부 | 최종 결정 | 제안, 근거 제시 |
| 작업 우선순위 | 최종 결정 | 제안, 근거 제시 |
| 여러 Product에 영향을 주는 기술 결정 | 승인 | 제안, 근거 제시 |
| 자신이 맡은 작업 안의 기술 결정 | 필요 시 의견 | 결정 |

- "자신이 맡은 작업 안": 해당 Ticket·이슈의 범위. 범위를 넘는 변경은 PM 승인
- 여러 Product 영향 여부가 불명확하면 PM에게 확인
- 기술 결정 중 규칙으로 남길 사안은 결정 기록(`decisions/`)으로 작성

## 접근 권한 보유 규칙

### 전원 보유

| 권한 | 범위 |
|---|---|
| 저장소 쓰기 | 5개 Product 저장소 전체 |
| AWS | 읽기 전용 |
| Terraform | `plan` |

### 2명 이상 보유 (PM 포함)

| 권한 | 규칙 |
|---|---|
| AWS 관리자 | 2명 이상 |
| Terraform `apply` | 2명 이상 |
| 운영 배포 승인 | 2명 이상. 작성자와 승인자는 서로 다른 사람 |
| 경보 수신 그룹 소유자 | 2명 이상 |
| 시크릿 읽기·쓰기 | 2명 이상 |
| GitHub 조직 소유자 | 2명 이상 |

- 한 사람이 빠져도 해당 권한을 행사할 수 있게 하는 것이 목적
- 보유자 목록은 팀 Notion에서 관리. 이 저장소에 적지 않음
- 기수 교체 시 보유자 변경과 회수 확인: PM
- 보호 리소스(RDS, S3, CloudFront)의 `delete`·`replace`가 plan에 나오면 승인 없이 apply하지 않음(product-infra 현행 규칙)

## 이견 조정

| 순서 | 방법 |
|---|---|
| 1 | 제안자가 근거(대안, 영향, 되돌리는 방법)를 이슈나 PR에 기재 |
| 2 | 당사자끼리 합의 |
| 3 | 합의 실패 시 PM이 결정하고 이유를 한 줄 기록 |
| 4 | 여러 Product에 영향을 주거나 규칙이 바뀌면 결정 기록 작성 |

- 결정 후 반대 의견은 기록으로 남김. 재검토는 되돌림 조건이 관측될 때 요청
- PM 결정에 대한 이의 제기: 이슈나 PR에 근거(대안, 영향)를 적어 재검토를 요청함. PM은 다음 정기 회의에서 답하고 결과를 결정 기록에 남김. Product Engineer 2명 이상이 반대하면 팀 회의 안건으로 올려 다시 정함

## 현재 체계에서 없어지는 것

| 현재 | 새 체계 |
|---|---|
| Lead, PO, 파트 PM 3단계 | PM 1명, Product Engineer 3명 |
| 파트(FE, BE) 단위 R&R | 담당 영역 고정 없음 |
| 에스컬레이션 경로(파트 PM → PO → Lead) | 없음. 결정은 PM |
| 파트 PM의 파트 내 기술 결정 권한 | Product Engineer의 작업 범위 내 결정 |
| Infra 기술 결정을 PO가 보유 | 일반 규칙 적용. 여러 Product 영향 시 PM 승인 |

- 기존 사례(RDS 8.0 → 8.4 업그레이드)처럼 서비스 중단이 있는 인프라 작업: 다운타임 승인과 일정 확정은 PM
