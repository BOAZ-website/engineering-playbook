# 접근 권한

보유 규칙의 기준은 `org/roles-and-authority.md`의 "접근 권한 보유 규칙". 이 문서는 요청·부여·회수 절차를 다룸. 보유자 이름과 계정은 적지 않음(팀 Notion 관리)

## 결정 사항

| 항목 | 규칙 |
|---|---|
| 기본 원칙 | 최소 권한. 작업에 필요한 권한만 부여 |
| 핵심 권한 | 2명 이상 보유(PM 포함) |
| 운영 배포 | PR 작성자·머지한 사람은 그 배포를 승인하지 않음 |
| 기수 교체 | 부여·회수를 PM이 확인 |

- 근거: 한 사람이 빠져도 해당 권한을 행사할 수 있어야 함
- 근거: 작성자가 직접 승인하면 검토 단계가 의미를 잃음

## GitHub 조직 설정

PM 결정(2026-11-29). 설정 변경은 조직 소유자가 함

| 항목 | 규칙 | 현황(2026-11-29) |
|---|---|---|
| 2단계 인증(2FA) | 조직 멤버 전원 필수. 켜면 2FA가 없는 멤버는 조직에서 빠지므로, 켜기 전에 전원이 2FA를 설정했는지 확인함 | 꺼짐 |
| 멤버 기본 권한 | Read. 저장소 쓰기는 팀 단위로 줌(기수 팀에 저장소별 Write, playbook은 PM 팀 Maintain) | Write. 쓰기 권한이 기본 권한에서 나오고 있어 팀별 Write를 먼저 준 뒤 Read로 바꿈 |
| 저장소 생성 | 조직 소유자만. 새 저장소는 `conventions/repos.md` "새 저장소 추가" 절차를 따름 | 멤버 누구나 가능 |
| 외부 협력자(outside collaborator) | PM 승인 후 추가. 기한(절대 날짜)을 정하고 기한 후 회수 | 0명 |

- 근거: 기본 권한이 Write이면 새 멤버가 모든 저장소에 바로 쓸 수 있어 최소 권한 원칙과 맞지 않음. 2FA가 없으면 계정 하나가 털렸을 때 공개 저장소와 배포가 함께 위험해짐
- Actions 기본 권한, Dependabot, secret scanning 같은 저장소 보안 설정은 `conventions/repos.md` "룰셋 표준"의 "보안 설정"

## 요청과 부여 절차

| 순서 | 작업 | 담당 |
|---|---|---|
| 1 | 권한 요청 이슈 또는 팀 메신저 요청. 필요한 권한, 이유, 필요 기간 기재 | 요청자 |
| 2 | 최소 권한 기준으로 승인 여부 결정 | PM |
| 3 | 권한 부여 | 해당 권한 보유자 |
| 4 | 팀 Notion의 보유자 목록 갱신 | PM |
| 5 | 부여 확인 | 요청자 |

- 임시 권한은 기한(절대 날짜)을 정하고 기한 후 회수
- 시크릿 값은 개별 전달. 저장소와 공개 문서에 적지 않음
- 로컬 환경 값 전달 방식: 무료 비밀번호 관리자의 팀 공유 보관함 사용. 1:1 메시지, Notion, 저장소에 값을 적지 않음. 기수 교체 때 보관함 권한 회수(`org/handover.md`)

## 운영 배포 승인 규칙

| 규칙 | 내용 |
|---|---|
| 승인자 | PR 작성자·머지한 사람이 아닌 사람. 26&27기는 `2nd-PMO` 팀, 27&28기부터는 그 기수의 PM 팀 + Product 담당자 1명. 머지 주체와 승인 짝은 `process/release.md` "운영 배포 승인" |
| 작성자 단독 머지 | 금지. 리뷰 승인 후 작성자가 머지 |
| hotfix | 리뷰어 1명 승인. 작성자는 승인 불가 |
| 인프라 보호 자원 변경 | plan 검토 후 승인(`products/infra.md`) |

## 기수 교체 시 회수

| 순서 | 작업 | 담당 |
|---|---|---|
| 1 | 후임 보유자 지정, 팀 Notion 보유자 목록 갱신 | PM |
| 2 | 후임에게 권한 부여 | 현재 권한 보유자(퇴임 전) |
| 3 | 후임 계정으로 실제 접근 확인(예: 로그인, 읽기 조회, 테스트 승인 등 권한별 확인 방법) | 후임 |
| 4 | 퇴임자를 제외하고 권한별 유효 보유자가 2명 이상인지 확인 | PM |
| 5 | 퇴임자 권한 회수(저장소, AWS, 조직, 경보 수신 그룹, 시크릿) | 남는 권한 보유자 |
| 6 | 확인 결과(권한별 후임, 접근 확인 일자, 회수 일자)를 인수인계 이슈에 기록 | PM |

- 회수를 먼저 하면 권한을 줄 사람이 없어지거나 후임이 실제로 쓰지 못하는 상태가 생김. 조직 소유자·AWS 관리자처럼 권한을 줄 수 있는 권한은 반드시 후임 접근 확인 후 회수
- 전체 절차: `org/handover.md`
- AWS 계정의 발급·변경·회수 세부: `org/aws-access.md`
