# PM 판단 가이드

절차(배포 승인, 리뷰 규칙 등)는 다른 문서에 있음. 이 문서는 PM이 애매한 상황에서 판단하는 기준을 적음. 27&28기부터 적용되며, 26&27기 Lead·PO의 결정권을 PM이 모두 맡음.

## 1. 역할과 경계

- PM은 결정을 직접 내리기보다 선택지와 장단점을 정리해 결정하는 것이 기본. 단 "3. PM이 직접 결정할 것"의 항목은 PM이 직접 결정
- 26&27기 Lead(최종 결정, 대표진 소통, 인력 배정, Product 전체 기술 결정)와 PO(일정·리소스, 인프라 기술 결정)의 권한은 PM이 맡음
- 26&27기 파트 PM(파트 내 기술 결정)의 권한은 Product Engineer가 맡음
- 사람의 기억 대신 반복되는 장치(주간 회의, 상태 보고, 결정 기록)로 확인함 (참고: Amazon TPM의 mechanism 개념)

## 2. 우선순위 (일이 충돌할 때)

| 순위 | 일 |
|---|---|
| 1 | 진행 중인 심각도 "높음" 장애의 완화: 서비스 전체 중단, 데이터 손상 위험, 보안 문제(`process/incident.md` "심각도") |
| 2 | 모집 일정에 걸린 일(서류 모집 시작, 면접, OT, 세션 시작 날짜에 걸린 작업) |
| 3 | 심각도 "중간" 장애(일부 기능 중단, 성능 저하) |
| 4 | 운영진 요청 |
| 5 | 개선 |

- 심각도 높음 장애는 모집 자체를 막으므로 모집 준비보다 먼저 완화함. 완화 후 원인 수정은 모집 일정과 비교해 PM이 정함
- 밀 수 없는 날짜에 걸린 작업은 범위를 줄여서라도 날짜를 지킴. 필수 / 있으면 좋음 / 미룸 순서로 자름 (참고: Basecamp Shape Up의 "고정 시간, 가변 범위")
- 연간 운영 일정은 `process/release.md` "연간 운영 일정" 절 참조

## 3. PM이 직접 결정할 것 (되돌리기 어려운 결정)

| 항목 | 비고 |
|---|---|
| 보호 자원(RDS, S3, CloudFront)의 삭제·교체 | 사전 승인 필요 |
| 보호 자원의 설정·권한 변경(예: S3 접근 정책, CloudFront 동작, RDS 파라미터) | 단일 Product 안의 변경이어도 사전 승인 필요 |
| 서비스가 멈추는 작업(예: 26&27기의 RDS 8.0 → 8.4 업그레이드) | 다운타임 승인과 일정 확정 |
| DB 시점 복원 | |
| 인증 방식 변경 | |
| 여러 Product에 영향을 주는 변경 | |
| 시크릿 교체 | |

- 판단 질문: "되돌리는 데 드는 비용이 큰가?" 크면 PM이 결정하고, 작으면(UI 문구, 라이브러리 버전 등) Product Engineer가 빠르게 결정 (참고: 되돌릴 수 있는 결정과 없는 결정의 구분)
- PM 결정은 결정 기록(`decisions/`)에 남김
- 보호 자원 규칙은 `products/infra.md` "보호 리소스 규칙" 참조

## 4. 티켓 우선순위 (Notion 티켓)

| 우선순위 | 기준 |
|---|---|
| 긴급 | 심각도 높음 장애, 또는 모집·운영이 막힘 |
| 높음 | 이번 스프린트 목표 |
| 중간 | 다음 스프린트 |
| 낮음 | 여유가 있을 때 |

- 2절 우선순위와 같은 기준. 심각도 높음 장애는 모집·운영이 계속되더라도 긴급

## 5. 기술 결정 범위

| 결정 주체 | 범위 |
|---|---|
| Product Engineer | 한 Product 안의 구현 방식, 라이브러리 선택, 구조 |
| PM | 3절 항목, 여러 Product에 걸친 결정 |

- 위임한 구현이나 인프라 apply 실행이라도 3절 대상(보호 자원 설정·권한 변경 등)이면 PM 사전 승인 필요

## 6. 위임과 직접 확인

위임 수준 표 (참고: Management 3.0 Delegation Board)

| 영역 | 수준 |
|---|---|
| 코드 리뷰 승인 | 맡김(`conventions/code-review.md`) |
| 운영 배포 승인 | 규칙대로(`process/release.md` "운영 배포 승인") |
| 한 Product 안의 기술 결정 | 맡김 |
| 인프라 apply(보호 자원 변경 없음) | 상의 후 진행. Product Engineer가 코드 PR과 plan 결과를 PM에게 공유하고, apply는 PM이 실행 |
| 3절 항목 | PM 결정 |

PM이 하는 일과 팀원에게 맡기는 일

| 일 | 담당 | 내용 |
|---|---|---|
| PR 리뷰 | 맡김 | Product Engineer끼리 리뷰함(`conventions/code-review.md`). PM은 3절 항목이 걸린 PR만 직접 확인 |
| 인프라 apply | PM | 2026-11-25 기준 apply 워크플로(STA-11)가 없어 PM이 로컬에서 실행함. 워크플로 도입 후에는 `main` 머지 때 워크플로가 실행하고, PM 팀이 `production` 승인으로 apply를 허가함 |
| 결정 기록 작성 | 작업 담당 | 결정이 나온 작업을 하는 사람이 작업 중에 바로 씀. PM이 따로 모아 쓰지 않음 |
| Notion 티켓 상태 갱신 | 티켓 담당 | 각 팀원이 자기 티켓의 상태를 직접 갱신함. PM은 주간 회의에서 어긋난 티켓만 확인 |
| Notion 티켓 생성 | 팀원 또는 PM | 누구나 만들 수 있음. 팀원이 만들면 PM에게 알림. PM이 우선순위와 스프린트 배정을 확인함. 생성 담당과 사전 승인 기준은 `process/dev-cycle.md` "티켓 생성과 배정" |

## 7. 상태 보고

| 대상 | 시점 |
|---|---|
| 팀 내부 | 주간 스프린트 회의 |
| 대표진 | 시즌 전후, 필요할 때 |
| 예외(즉시 보고) | 시즌 전환(season-up·season-down) 중 장애와 심각도 높음 장애 |

- 예외 건은 발견 즉시 PM에게 알리고 `process/incident.md`에 따라 대응. 주간 회의를 기다리지 않음

주간 보고 양식(팀 Notion에 작성)

- 전체 상태(초록/노랑/빨강)와 근거 1문장
- 진행
- 리스크 상위 3개(담당 역할)
- 결정 필요 사항(무엇을, 누가, 언제까지)
- 다음 주 계획

빨강 기준: 밀 수 없는 날짜를 못 지킬 위험, 운영 장애 위험. 빨강은 문책이 아니라 도움 요청 (참고: 상태 보고 템플릿 관행)

## 8. 리스크 관리

- 리스크·가정·이슈·의존성을 한 표로 관리(RAID). 열은 유형, 내용, 담당 역할, 다음 검토일. 팀 Notion에 둠
- 시즌 전환처럼 되돌리기 어려운 큰 작업 전에는 30분 사전 실패 검토(pre-mortem)를 함. "이미 실패했다"고 가정하고 원인을 각자 적음 (참고: Gary Klein, HBR 2007)
- Product 간 의존성(예: 백엔드 DTO 변경 → 프론트엔드 타입 재생성)은 `contracts/` 참조

## 9. 판단 사례

사례마다 상황, 선택지, 결정, 이유, 결과를 적음. 후임 PM이 비슷한 상황에서 판단 순서를 따라 할 수 있게 하는 것이 목적

### 사례 1. 운영 DB 메이저 버전 업그레이드(26&27기, MySQL 8.0 → 8.4)

| 항목 | 내용 |
|---|---|
| 상황 | 운영 DB(RDS MySQL 8.0)의 AWS 표준 지원이 2026-07-31에 끝나 8.4 강제 자동 업그레이드 대상이 됨. 유료 확장 지원을 쓰지 않으면 AWS 유지관리 시간에 임의로 올라감. 단일 EC2와 Single-AZ RDS 구조라 배포와 업그레이드 모두 다운타임이 생김 |
| 선택지 | ① 유료 확장 지원으로 8.0 유지 ② AWS 자동 업그레이드를 기다림 ③ 팀이 정한 시점에 직접 업그레이드 |
| 결정 | ③ 통제된 시점(밤 23~24시)에 직접 업그레이드. 다운타임 승인과 일정 확정은 이 가이드 3절 기준으로 PM이 함 |
| 이유 | ①은 비용이 계속 듦. ②는 시점을 모르고 사전 점검 없이 올라가 장애 대응이 어려움. ③은 사전 점검과 되돌리기 지점을 확보할 수 있음 |
| 결과 | 8.4로 업그레이드 완료. 읽기 기능 전반과 쓰기(리크루팅 알림 신청) 정상 확인. 다운타임은 예상 범위(10~30분) 안 |

판단 순서에서 따라 할 점

- 호환성 검토로 사전에 해결할 위험을 찾음: DB 접속 계정의 인증 방식(8.4에서 구 방식 기본 비활성), DB 시간대 파라미터(새 파라미터 그룹으로 옮기지 않으면 저장 시각이 9시간 어긋남)
- 위험을 업그레이드 당일 전에 처리함: 새 파라미터 그룹 생성과 시간대 값 이전, 새 인증 방식을 임시 계정으로 미리 접속 확인, 백업·유지관리 시간을 새벽으로 이동, AWS 자동 업그레이드 예약 여부 확인
- 한 번에 하나씩 바꿈: 8.0에서도 동작하는 코드 변경을 먼저 릴리스하고 정상 동작을 확인한 뒤, DB 업그레이드를 단독 변경으로 실행. 문제가 생기면 원인을 코드와 DB 중 하나로 좁히고 되돌리기도 따로 할 수 있음
- 되돌릴 수 없는 작업 전에 되돌리기 지점을 만듦: 메이저 업그레이드는 그 자리에서 되돌릴 수 없어 직전 수동 스냅샷을 만들고, 실패하면 스냅샷에서 복원하기로 정함
- 시작·완료를 공지하고, 업그레이드 후 검증 항목(엔진 버전, 시간대, 스키마 검증 기동, 읽기·쓰기 동작)을 미리 정해 둠
- 범위 밖 개선(DB 접속 TLS 전환)과 정리 작업(구 파라미터 그룹, 되돌리기용 스냅샷)은 후속으로 분리함
